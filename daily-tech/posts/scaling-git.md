## 为什么 Codex 越强，Git 反而越容易成为瓶颈？

首先需要理解，Coding Agent 改变的不只是代码生成速度，还包括整个软件开发过程的并行度。

传统开发中，一名工程师通常集中处理少数几个任务。

开发者创建一个分支，在本地修改代码，运行测试，然后 Push 到远程仓库。

如果测试失败，继续修改，再次提交。

完成以后，将分支合并回主分支。

这个流程虽然可以并行，但人类工程师的注意力天然限制了同时推进的任务数量。

即使一名工程师非常高效，也很难同时亲自编写、调试和验证几十个不同功能。

Codex 改变了这个条件。

同一名工程师可以要求不同 Agent 同时修改多个模块。

每个 Agent 可以拥有自己的代码分支和工作环境。

当这些 Agent 完成任务，它们会各自提交代码，触发 CI 流程。

而一次 CI 又可能启动多个构建、测试和分析任务。

这些任务需要从 Git 仓库获取相应的代码版本。

因此，一个 Agent 完成一次 Push，可能进一步触发多个 Fetch、Clone 和测试作业。

随着 Agent 数量增加，Git 请求量增长得可能比人类工程师数量快得多。

OpenAI 在文章中说明，自 2025 年底开始，其内部 Monorepo 已经明显出现这种压力。

Git Fetch 和 Push 越来越慢。

合并操作出现失败。

部分时候可靠性下降到 90% 以下。

这里的关键并不是 Git 无法处理大型仓库，而是 OpenAI 原有的 Git 服务架构，没有针对如此密集的并发工作进行优化。

**当一个工程师通过 Agent 放大自己的工作能力，代码仓库承受的负载，也会被同步放大。**

这意味着 Coding Agent 的生产率提升可能在其他基础设施中制造新的瓶颈。

例如，代码审查、测试资源、构建缓存、持续集成和最终部署系统，都可能遇到类似问题。

OpenAI 这次最先需要重构的，是源代码管理系统。[OpenAI](https://openai.com/index/scaling-git-at-openai/)

## 问题并不在 Git 的核心数据模型，而在我们通常怎样部署 Git Server

理解 Pando 为什么能够改善性能，需要先弄清楚 Git 本身的存储机制。

Git 最重要的设计之一，是它主要通过不可变对象保存代码历史。

例如，假设一个仓库里有 parser.py 和 README.md。

当开发者修改 parser.py 后，Git 不需要重新保存整个仓库的所有文件。

它会为新的文件内容创建一个 Blob 对象。

没有变化的 README.md 可以继续引用以前的 Blob。

Git 同时使用 Tree 对象表示目录结构，并使用 Commit 对象连接文件快照与历史记录。

每个对象都由其内容计算得到的哈希值标识。

因此，只要对象内容没有变化，标识就不会变化。

这让相同对象可以被不同提交共享，也使 Git 能够高效保存大量历史版本。

而分支与这些不可变对象不同。

例如，`refs/heads/main` 是一个可以变化的引用，它指向当前主分支的某个 Commit。

当开发者向主分支提交新代码，实际上会产生新的 Commit，并更新 main 指向的位置。

因此，Git 仓库里存在两种性质非常不同的信息：

**大量不可变的历史对象，以及少量不断变化的分支引用。**

这个区别是 Pando 架构设计的起点。

因为不可变对象天然适合缓存、复制和分布式存储。

真正需要协调并发更新的，是分支引用。

OpenAI 认为，传统 Git Server 在这两种数据的协调方式上，可以做出不同于过去的选择。[OpenAI](https://openai.com/index/scaling-git-at-openai/)

### Git Packfile 为什么如此重要？

Git 不会在每次网络传输时，把所有文件逐个发送。

它通常使用 Packfile，把多个 Git 对象压缩成一个文件。

如果两个文件版本非常相似，Git 还可以通过 Delta Compression，只记录部分差异来节省空间。

例如，一个大型源代码文件只有几行发生变化，就不必完整重复保存每个版本。

当客户端执行 Fetch 时，会告诉服务器自己已经拥有哪些 Commit，以及希望获取哪个版本。

这些信息通常称为 have 和 want。

服务器据此计算客户端缺少的对象，然后构造 Packfile。

这是一项非常聪明的设计。

因为不同开发者拥有的历史可能不同。

服务器可以为每个人生成尽量精简的增量数据。

但是，当同一个仓库同时服务成千上万个客户端时，这种个性化也会带来成本。

服务器需要不断计算每个客户端缺少什么。

然后为不同请求生成不同 Packfile。

即使两个客户端实际上需要非常相似的代码，服务器也可能重复执行大量压缩和对象计算工作。

更麻烦的是，这种针对客户端定制的结果不容易被重复缓存。

这就是 OpenAI 看到的一项重要性能机会：

**如果能够让多个客户端重复下载相同的 Packfile，就可能把 Git Fetch 从高 CPU 消耗的计算任务，转化成更加容易扩展的数据传输任务。**

而这需要改变服务器与客户端协商历史对象的方式。[OpenAI](https://openai.com/index/scaling-git-at-openai/)

## 为什么传统分布式 Git 架构很难同时支持大量写入？

OpenAI 在设计 Pando 时，比较了两种常见的分布式存储思路。

它们都可以保证数据一致性，但在高度并发的场景下具有不同的成本。

一种方案是让多个 Git Server 保存完整的仓库副本。

当某个客户端 Push 新代码时，接收请求的服务器需要把相关数据复制给其他服务器。

随后，通过分布式协调协议，让多个副本同意更新某个分支。

OpenAI 在文章中使用了基于 Three-Phase Commit（三阶段提交）的模型来说明这种方式。

它的优势是，不同服务器能够对仓库状态形成较为一致的视图。

但是，这也意味着写入需要多次网络通信。

部分阶段还必须等待其他副本确认。

如果大量客户端同时 Push，协调开销就可能越来越明显。

另一种方案则通过共享的 Write-Ahead Log，简称 WAL，记录仓库更新。

WAL 可以理解为在正式应用修改前，先记录一条可恢复的变更日志。

多个服务器可以并行上传 Git 数据，但它们仍然需要通过共享的日志或 Manifest 确定更新顺序。

在 OpenAI 研究的方案中，发布新版本需要使用 Compare-and-Swap 操作修改共享 Manifest。

这会形成一个竞争点。

即使两个 Agent 修改的是完全不同的分支，它们仍然可能需要依次更新同一份共享元数据。

这有点像一家银行拥有很多柜台，却要求所有柜台最终必须通过同一台机器登记每笔业务。

增加柜台数量能够提高部分处理能力，却不能让那台中央登记机器无限加速。

OpenAI 发现，问题不是传统分布式存储方法不正确。

而是它们提供的某些一致性保证，对于自己的实际工作负载而言过于昂贵。[OpenAI](https://openai.com/index/scaling-git-at-openai/)

## Pando 最重要的决定：为什么整个仓库不一定需要同一个时间点的状态？

这是我认为全文最值得认真理解的架构选择。

传统分布式系统往往追求较强的一致性。

例如，某个客户端在同一时刻读取所有分支，希望得到一份严格一致的仓库快照。

但是，OpenAI 发现，其开发者与 Coding Agent 通常并不需要这种保证。

假设两个 Agent 分别修改分支 feature-A 和 feature-B。

它们彼此独立。

Agent A 只需要确保自己的提交正确进入 feature-A。

Agent B 只需要确保自己的提交正确进入 feature-B。

没有必要仅仅因为它们属于同一个仓库，就让所有更新经过一个全局顺序。

因此，Pando 放宽了仓库级别的一致性要求。

它重点保证每个独立分支的更新具有正确顺序。

同时，读取某个分支时，客户端必须能够获得该版本所依赖的历史对象。

这对应一种较弱的全局一致性设计，可以理解为以因果一致性（Causal Consistency）为核心，同时保证单个 Ref 更新的串行化语义。

例如，Agent A 创建了一个新 Commit，其父节点是另一个已经存在的 Commit。

那么任何成功读取新 Commit 的客户端，都必须能够获取对应的父节点和文件对象。

Pando 不能让用户看到一个 Commit，却无法获取该 Commit 引用的代码内容。

但是，如果客户端同时读取两个互不相关的分支，它不一定看到它们处于完全相同的全局时间点。

例如，某个客户端可能看到 feature-A 的较新版本，以及 feature-B 的较旧版本。

另一个客户端则可能恰好看到相反的组合。

对于要求整个仓库具有原子级全局快照的应用，这可能不够。

但对于大量独立 Agent 在不同分支上工作的场景，OpenAI 认为这种权衡是可以接受的。[OpenAI](https://openai.com/index/scaling-git-at-openai/)

**Pando 不是通过让所有操作变得更快来扩展系统，而是通过取消工作负载实际上不需要的全局协调。**

这是非常典型、也非常值得学习的分布式系统设计思想。

当工程师希望提高吞吐量时，首先需要确认系统究竟必须保证什么。

如果某种昂贵的保证不是业务真正需要的，那么放宽它，可能比购买更快的服务器更有效。

## Pando 如何在保持 Git 协议兼容的情况下，实现分支独立写入？

Pando 把 Git Packfile 存入可横向扩展的 Blob Storage。

同时使用独立的 Metadata Store 保存分支引用及其版本历史。

当客户端执行 Push，服务器接收新的 Packfile，并且在接收数据流的过程中进行验证。

它不需要先把所有对象完整展开到本地 Git 仓库。

验证完成后，服务器通过元数据事务记录新的分支版本，并以原子方式更新对应 Ref 指针。

这些元数据包括新分支指向的 Commit、相关 Packfile，以及这个版本依赖哪些此前的历史。

由于不同分支拥有不同的 Ref 指针，服务器可以并行处理互不相关的分支更新。

真正需要冲突处理的，是多个客户端同时试图修改同一个 Ref。

例如，两个 Agent 同时准备更新 main。

如果它们都认为 main 仍然指向同一个旧 Commit，那么服务器必须确保不会无条件接受两次相互冲突的更新。

Pando 使用类似原子 Compare-and-Swap 的方式处理这种竞争。

但如果一个 Agent 修改 feature-A，另一个修改 feature-B，就不必因为全局仓库锁而相互等待。

根据 OpenAI 的架构说明，完成一次 Push 的关键同步元数据操作数量能够保持在 **O(1)** 的量级。

这里的 O(1) 指关键元数据访问次数不会随着仓库历史规模线性增加，并不是说任意大小的 Push 都具有固定执行时间。

毕竟传输一个巨大 Packfile，仍然需要与文件大小相对应的网络和存储时间。

这套设计让 Pando 的计算节点主要负责请求协商、验证和元数据更新，而不必保存并反复处理完整仓库。

因此，系统可以通过增加服务器、Blob Storage 和元数据存储容量，扩大整体并发能力。[OpenAI](https://openai.com/index/scaling-git-at-openai/)

## 为什么 OpenAI 故意让某些 Git Push 发送更多数据？

这可能是文章中最反直觉的工程决策。

通常，我们希望 Git Push 尽量小。

如果服务器已经拥有某些对象，客户端就不需要重复发送。

为了做到这一点，传统 Git Server 可以向客户端展示大量已经存在的分支引用。

客户端根据这些信息，判断哪些对象可以省略。

这样得到的 Packfile 往往更加精简。

但 Pando 发现，Packfile 越依赖客户端与服务器之间特殊的历史协商，它就越难被其他客户端直接复用。

例如，Agent A 发送一个 Packfile 时，假设服务器已经拥有分支 X 和 Y 上的若干对象。

它可能省略这些对象。

但之后 Agent B 想下载同一段代码，如果 Agent B 没有那些特殊的历史对象，就不能直接使用这个 Packfile。

服务器还需要补充缺失内容。

因此，OpenAI 选择了另一种权衡。

当客户端准备 Push 一个新功能分支时，Pando 默认主要向它展示指定的主干分支，作为双方共同拥有的历史基础。

客户端据此生成 Packfile。

它可能包含某些此前在其他分支出现过的对象。

所以单次 Push 未必达到理论上的最小网络传输量。

但它的依赖关系会更加简单。

只要另一个客户端拥有对应的主干历史，就更容易直接使用这份 Packfile。

这使上传的数据能够在后续下载过程中重复使用。

OpenAI 还指出，对于拥有数百万分支的仓库，如果向客户端展示全部 Ref，单是分支列表就可能超过 **100 MiB**。

而只展示主干引用，可以让协商信息的规模基本不随分支数量增长。

这种策略同样有代价。

如果开发者反复向同一个功能分支 Push，或者在多个功能分支之间建立复杂的堆叠关系，客户端可能需要重复发送主干之外的对象。

但 OpenAI 观察到，在自己的 Monorepo 工作负载中，由这种策略生成的 Packfile 中位大小不到 **20 KiB**，第 99 百分位数也低于 **3 MiB**。

所以它认为，增加少量上传数据，换取后续的大规模复用，是合理的选择。[OpenAI](https://openai.com/index/scaling-git-at-openai/)

这实际上是把优化目标从单次请求，转移到了整个系统。

**单个 Push 传输最少的数据，不一定意味着成千上万个 Agent 同时工作时的总成本最低。**

如果一次稍大的上传能够被大量客户端复用，系统最终节省的 CPU、磁盘 I/O 和网络协商工作，可能远大于上传阶段增加的成本。

## 真正让 Fetch 扩展到巨大规模的，是 Git 协议里一个早已存在的功能

Pando 在读取方面利用了一项并不新的 Git 协议能力：`packfile-uri`。

传统 Git Fetch 通常由服务器直接向客户端发送一份 Packfile。

但 Git Protocol v2 允许服务器向客户端提供一些 Packfile 的下载地址。

客户端可以通过这些地址获取相关数据。

这种机制的初衷之一，就是让服务器能够把大规模数据传输交给更加适合处理带宽负载的存储或 CDN 系统。

Git 官方文档已经提供了相应协议定义。[Git](https://git-scm.com/docs/packfile-uri)

OpenAI 发现，可以把这项能力使用得更加彻底。

Pando 不必为每一个 Fetch 重新计算并生成完整 Packfile。

它可以根据客户端已经拥有的 Commit，找到需要的历史版本，再从此前保存的 Packfile 中选择适当组合。

随后，服务器返回对应的 Packfile URI。

真正的数据传输，则交给一套名为 **Express** 的缓存服务。

Express 在不同地区缓存这些不可变 Packfile。

这样，当多个 Coding Agent 或 CI 作业需要相同代码时，它们可以从区域缓存直接下载，而不必每次都访问中心存储。

因为 Packfile 不会被修改，同一份缓存可以安全地被重复使用。

OpenAI 表示，其 Express 缓存的命中率超过 **99%**。

在测试中，采用标准云服务器的系统能够让 Clone 和 Fetch 充分利用 **10 Gbps** 网络连接。

但需要注意，这是 OpenAI 自己披露的特定测试结果，并不代表所有客户端、所有地区和任意网络条件下都能达到相同速度。[OpenAI](https://openai.com/index/scaling-git-at-openai/)

这项技术选择的真正价值，在于改变了服务器的角色。

传统 Git Server 需要大量参与具体数据的计算与组织。

Pando 则让服务器更多地负责判断需要哪些对象，再由缓存基础设施提供已经准备好的数据。

这与现代互联网内容分发有些相似。

视频服务不会在每次用户观看同一段视频时重新编码。

它会尽量重用已经编码并缓存的内容。

Pando 试图把相似的经济逻辑应用到 Git 数据分发中。

## 但是 Packfile 可以复用以后，又出现了一个新问题：历史版本可能产生数万个小文件

假设 OpenAI 的主分支每天发生几万次更新。

如果每次 Push 都产生一个独立 Packfile，那么一个几天没有更新本地仓库的工程师，在执行 Fetch 时可能需要下载数量巨大的小文件。

即使每个文件都很小，发起大量请求仍然会产生很高的延迟。

因此，Pando 需要一种方式，在保留 Packfile 复用优势的同时，减少下载文件数量。

OpenAI 采用了类似 **Log-Structured Merge Tree（LSM Tree）** 的后台合并机制。

LSM Tree 是数据库系统中常见的一类存储设计。

它通过先快速写入较小的数据单元，再在后台逐渐合并，改善读取效率。

Pando 把每次 Push 形成的原始 Packfile 称为 L0。

随后，后台任务可以将相邻历史版本对应的小 Packfile 组合成更大的覆盖范围。

这些覆盖范围逐渐形成 L1、L2 等层级。

OpenAI 披露，其生产仓库目前使用到 L4 级别。[OpenAI](https://openai.com/index/scaling-git-at-openai/)

这种分层结构有不同的作用。

首先，后台合并可以减少未来客户端需要下载的文件数量。

其次，多个 Packfile 合并以后，可以重新利用对象之间的相似性进行压缩。

更重要的是，这些层级本身能够帮助系统快速定位客户端需要的历史范围。

不必从最初版本开始，逐个检查所有 Push。

Pando 可以利用不同层级覆盖的历史区间，更快地寻找合适的 Packfile 组合。

OpenAI 将这种机制与 Skip List 的思想联系起来。

如果把客户端落后的版本距离记为 `Δ`，文章描述的 Fetch 元数据查找可以达到 **O(log Δ)** 的量级。

这意味着，即使客户端落后很多次提交，系统也不必为每个历史版本单独执行一次元数据查询。

这里还有一个值得注意的设计。

Pando 并没有在合并以后立即丢弃所有较小的旧 Packfile。

不同层级的文件仍然可以继续用于服务请求。

原因是，有些客户端只需要很小范围的数据。

对于这种请求，读取一个小 Packfile，可能比从高度压缩的巨大 Packfile 中提取少量对象更有效。

所以 Pando 保留不同粒度的数据组织方式，让系统根据请求选择合适的文件。

**这不是简单地把文件越合越大，而是让不同大小的缓存单元共同服务不同的读取需求。**

这种设计既考虑整体吞吐量，也考虑用户从发起 Fetch 到开始接收数据的延迟。

## Pando 最令人意外的部分：整套系统只用了十周就进入生产

如果只看前面的架构，Pando 已经是一套相当复杂的分布式存储系统。

它需要正确处理 Git 对象依赖。

需要保证同一分支上的并发写入不会相互覆盖。

需要处理不同客户端之间的因果历史。

还需要保证 Fetch 不会遗漏任何必须存在的对象。

如果出现错误，后果可能不是简单的请求失败。

它甚至可能影响代码历史的完整性。

因此，这类系统通常要求非常严格的测试和验证。

但 OpenAI 披露，Pando 从项目启动到生产部署，只用了约 **10 周**。

它的核心架构由一名工程师设计。

实现工作则大量依赖多个 Coding Agent。

少量工程师负责部署和验证。

Pando 于 **2026 年 4 月**开始处理生产流量，如今已成为 OpenAI Monorepo 的主要 Git 后端。[OpenAI](https://openai.com/index/scaling-git-at-openai/)

这并不代表 OpenAI 只用一名工程师就完成了全部工作。

公司拥有成熟的基础设施团队、内部工具、自动化测试环境和已有的 Git 服务系统。

Agent 的开发能力也依赖这些环境。

但是，这仍然展示了一种值得关注的新型软件开发组织方式。

人类工程师不必亲自编写每一行代码。

他们可以定义架构、约束和验证标准，再让多个 Agent 并行实现不同模块。

OpenAI 为 Pando 选择了 Rust，并尽量避免引入过多历史依赖。

Rust 的类型系统和内存安全机制能够帮助减少部分底层错误，但不能自动保证分布式协议正确。

因此，团队还建立了一套 Git Conformance Tests，用于检查实现是否符合标准 Git 行为。

此外，他们使用确定性模拟测试来寻找并发竞态条件、状态不一致和历史协商中的异常。

这里最有意思的，是 OpenAI 进一步使用了形式化方法。

团队让运行 GPT-6 Astra 的 Agent 编写 Lean 和 TLA+ 模型，对 Pando 的部分行为进行形式化描述。

Lean 可以用于形式化证明。

TLA+ 则常用于描述并验证并发和分布式系统中的状态变化。

Agent 不只是编写业务代码，还参与建立能够发现代码错误的数学模型。

OpenAI 表示，这些方法帮助团队发现并修复了实现中的缺陷。

另外，一些连续运行的 Agent 会话持续工作数百小时，用于寻找边界情况。

团队还使用具有高级网络安全研究能力的模型，持续对 Git 和 Pando 进行安全测试。[OpenAI](https://openai.com/index/scaling-git-at-openai/)

我认为这个案例最值得关注的，不是 AI 帮助程序员少写了多少代码。

而是**软件开发与软件验证，都开始能够通过 Agent 并行扩展。**

不过，形式化验证的存在并不意味着整个 Pando 系统已经获得端到端的数学正确性证明。报告没有提供这样的完整保证。

它说明的是，形式化工具正在实际参与复杂软件的工程验证，而不再只是少数研究项目中的实验手段。

## OpenAI 如何在不影响工程师工作的情况下，替换整个 Git 后端？

对于成熟的软件公司，开发新系统通常不是最困难的部分。

真正困难的是怎样把它放进生产环境。

OpenAI 不可能为了部署 Pando，让全体工程师停止工作，再把所有代码仓库一次性迁移。

因此，公司最初把 Pando 部署成原有 Git 后端前面的代理层。

它可以同时处理读取和写入，并将相关请求转发给旧系统。

这让新旧系统能够在迁移过程中保持同步。

同时，Pando 可以通过缓存减少旧系统需要重复处理的请求。

随着越来越多工作负载转移到新系统，Pando 的缓存逐渐积累了更多真实 Git 数据。

这反过来减轻了旧后端的压力。

随后，OpenAI 逐步迁移不同开发环境和内部服务。

公司还需要处理数百个依赖既有 API、Webhook 和仓库下载功能的集成。

为了帮助工程师迁移，团队开发了相关 Codex Skill。

开发者可以让 Codex 协助准备已有代码仓库和开发环境。

因此，Agent 不仅参与了新系统的开发，还参与了系统部署和用户迁移。

这与传统大型基础设施改造形成了很有意思的对比。

以前迁移工具链，往往需要工程师阅读大量文档，按照复杂流程修改环境。

现在，部分机械性迁移工作可以交给 Agent 完成。

不过，涉及生产环境权限、数据完整性和重大配置变更时，仍然需要明确的验证与审批机制。

OpenAI 披露，切换到 Pando 以后，合并可靠性改善，Git Push 中位延迟下降近 80%。

公司还表示，Pando 已经能够以相对少量 CPU 资源，处理每天接近 1 PB 的 Git 数据传输。

这些数字来自 OpenAI 内部生产环境，没有提供可以与 GitHub、GitLab 等产品直接比较的统一公开 Benchmark，因此不应将其解释成 Pando 已经在所有使用场景中优于其他 Git 服务。[OpenAI](https://openai.com/index/scaling-git-at-openai/)

## 这并不意味着 OpenAI 要取代 Git

文章最后还有一个重要的开源技术细节。

Pando 是新的 Git 后端，而不是要求所有开发者改用一种与 Git 不兼容的版本控制系统。

OpenAI 选择保留 Git，是因为大量现有工具都已经围绕 Git 建立。

开发者熟悉它的命令。

CI 平台支持它的协议。

编辑器、代码审查系统和开发工具也依赖 Git。

如果完全替换版本控制系统，即使新技术性能更好，也可能需要付出非常高的迁移成本。

因此，OpenAI 选择改善底层实现，而不是强迫用户改变工作习惯。

团队在开发过程中，也发现了标准 Git 客户端中的一些性能问题和边界错误。

例如，同时下载多个 Packfile 时，可能出现下载状态、清理和恢复方面的问题。

OpenAI 修复了部分问题，并把相关改进提交给上游 Git 项目。

团队还增加了更详细的性能追踪，以便区分一次慢速 Fetch 究竟花了多少时间计算 Packfile，以及多少时间用于实际数据传输。

其公开 Git 分支已经包含并行下载和索引 Packfile 等改进，并对部分 Git Push 协商机制进行了扩展。[OpenAI](https://openai.com/index/scaling-git-at-openai/)

因此，Pando 有可能给更广泛的 Git 生态带来技术收益。

不过，需要明确区分 Git 客户端的公开改进，与 Pando 整套后端架构的开放程度。

截至这篇文章发布时，OpenAI 还在探索如何将 Pando 背后的技术分享给更多用户，并没有宣布完整后端已经成为通用开源产品。

**能够通过公开 Git 协议使用一套系统，不等于这套系统的服务器实现已经完全开放。**

## 我的理解：AI Coding Agent 正在改变软件工程的基本工作单位

下面是我的延伸判断，不属于 OpenAI 已经通过实验直接证明的结论。

我认为《Scaling Git at OpenAI》最重要的价值，是揭示了软件工程的基本工作单位正在发生变化。

过去，我们通常以工程师人数衡量一个开发团队的规模。

十名工程师能够同时处理的任务数量，通常受到十个人的时间和注意力限制。

但当一个工程师可以管理多个 Agent，团队能够同时推进的任务数量，就不再简单等于工程师人数。

真正的约束可能转向其他地方。

例如，一个团队是否拥有足够快的 CI 系统。

是否能够及时审核大量代码修改。

是否具备可靠的自动化测试。

不同 Agent 修改同一个模块时，能否有效解决冲突。

以及每个任务完成以后，系统能否迅速把正确的代码交付给其他开发环境。

Git 只是其中一个环节。

但它是非常基础的环节。

如果代码仓库不能及时接受和分发修改，Agent 就可能不断等待。

这意味着，模型生成代码的速度再快，也无法完整转化成软件交付速度。

我认为未来评价 Coding Agent，不应该只看它每小时能写多少代码。

还应该衡量从任务提出到代码最终合并，并通过必要测试所需的完整时间。

**真正决定软件工程生产率的，不是代码生成吞吐量，而是经过验证、可以安全交付的有效变更吞吐量。**

Pando 只是 OpenAI 为提高这个吞吐量而进行的一项基础设施改造。

但同样的逻辑可能继续推动测试系统、构建平台、依赖管理和代码审查工具发生变化。

## 一个非常重要的工程启示：不要只想着让系统更快，而要重新检查系统究竟需要保证什么

Pando 的架构还提供了一个可以推广到其他分布式系统的思想。

传统软件往往默认需要尽可能强的一致性。

当系统无法扩展时，团队可能首先尝试增加服务器数量、优化数据库查询，或者购买更高性能的硬件。

但 Pando 的设计者先问了一个更加基础的问题：

对于大量独立代码分支，我们真的需要整个仓库始终具有全局一致的版本视图吗？

他们发现，大部分开发流程并不依赖这一点。

真正不可妥协的是，每条分支自身的更新顺序，以及 Git 对象历史的完整性。

于是，系统可以让不同分支独立更新，并通过不可变 Packfile 实现大规模数据复用。

这是一种通过调整语义要求来获得扩展能力的思路。

对于 AI Agent 系统，我认为它尤其重要。

因为 Agent 可能制造非常高的并发负载，却不一定需要每个操作都具备传统人工工作流中假定的全部保证。

例如，大量互不相关的实验任务可以独立运行。

但同一笔金融交易的重复执行必须严格受到限制。

不同研究任务之间可以采用相对宽松的状态同步。

但生产环境部署仍然需要可靠的版本控制和审计。

未来设计 Agent 平台，一个重要能力就是正确识别：

哪些操作可以放宽一致性要求，以获得更高的并发能力？

哪些操作必须保持严格的业务约束？

这比简单地把更多任务交给大模型更加关键。

## 对 AI 基础设施和软件工具行业，有什么商业启示？

这篇文章让我更加关注 Coding Agent 基础设施中的一个潜在机会：**当代码生产成本下降以后，原本不那么昂贵的协调和验证工作，可能开始成为整个系统最重要的成本。**

过去代码仓库主要处理人类开发节奏下的工作量。

未来，大型团队可能同时运行成千上万个 Agent。

这种情况下，版本控制、构建缓存、自动化测试、代码审查和部署系统的重要性可能上升。

但它不意味着每家公司都需要开发自己的 Pando。

大多数中小型软件项目，继续使用 GitHub 或 GitLab 提供的标准服务就可能足够。

OpenAI 的 Monorepo 规模和 Agent 并发量属于特殊场景。

因此，真正值得关注的是：类似的负载模式会不会随着 Coding Agent 普及，逐渐扩散到更多大型企业？

如果确实如此，那么能够降低每次代码变更协调成本的产品，就可能获得新的市场机会。

对云基础设施而言，这也可能改变资源消耗结构。

随着更多任务通过 Agent 自动完成，企业可能增加代码编译、CI 测试和临时开发环境的使用量。

但这些工作负载与大模型推理不同。

它们可能更多消耗通用 CPU、存储 I/O、网络带宽以及缓存资源。

因此，Agent 产业的基础设施需求，不应该只理解为训练和推理 GPU。

整个软件工程工具链都可能出现新的资源需求。

不过，这些需求是否形成高利润市场，还要看软件供应商能否提供足够独特的能力，以及大型云平台会不会把它们整合成相对廉价的基础服务。

## 最后的判断：AI Agent 不只是让软件开发更快，而是在迫使我们重新设计软件开发系统

我认为《Scaling Git at OpenAI》真正值得记住的，并不是每天传输 1 PB 数据，或者 Git Push 延迟降低近 80%。

这些数字非常亮眼，但属于 OpenAI 的特定工作负载。

更重要的是，这篇文章展示了一种正在出现的新型技术循环。

AI Agent 提高软件生产速度。

软件生产速度提高，让传统开发工具遇到扩展瓶颈。

工程师借助 AI Agent，重新设计这些基础设施。

新的基础设施又允许更多 Agent 同时工作。

这可能形成一种持续改善的软件工程反馈循环。

但它并不保证 AI Agent 能无限提高生产率，因为每次扩展都可能把瓶颈转移到另一个环节。

代码生成速度提高以后，测试可能成为瓶颈。

测试速度提高以后，代码审查可能成为瓶颈。

代码审查自动化以后，系统架构、产品需求和最终责任划分又可能成为限制因素。

因此，未来软件行业最重要的竞争，不一定是谁拥有生成代码速度最快的模型。

更可能是谁能够把模型、工程师、开发环境、测试、版本控制和生产部署组织成一套可靠的系统。

**OpenAI 用 Codex 帮助自己重新设计 Git 基础设施的案例，说明 Coding Agent 已经不仅是程序员的辅助工具，而开始成为软件基础设施本身的生产者。**

我认为这比让 AI 写出更多代码更加重要。

因为当创建软件越来越便宜，真正稀缺的能力，将逐渐转向如何让越来越多的软件变更能够被正确理解、有效验证、安全合并，并稳定运行。

而 Pando 证明，至少对于 OpenAI 所面临的代码仓库规模，这种转型已经不再只是未来的软件工程设想，而是正在生产环境中发生的现实。
