# Claude 的 API 迁移到 Rust：CPU 开销下降 70%，真正难的却是验证

2026 年 11 月 25 日，Lance Martin、Jake Eaton、Arvin Aminpour、Emma Webb、Bharat Mediratta 和 Ravi Trivedi 在 Anthropic 工程博客发表了免费公开的长文 [Migrating our Messages API to Rust](https://www.anthropic.com/research/migrating-api-to-rust)，并给出了生产环境的数据与工程过程图。全文约需 15 分钟阅读。它记录了一次颇有代表性的技术迁移：当 AI 已经能迅速写出新系统，如何证明它能够接管仍在高速演进的旧系统？

## 从局部优化到整体迁移

Messages API 从 2024 年初到 2026 年秋的请求量扩大约 1,800 倍。随着输入校验、提示词构造、安全筛查和输出流处理逐渐复杂，原来的 Python 服务负担越来越重。局部替换输出解析器只节省约 8%–10% 的 CPU 开销，还引入每个 token 三次跨语言传递。Claude 约一周就完成了 Rust 核心请求路径的初版。

[Messages API 的接口文档](https://platform.claude.com/docs/en/build-with-claude/working-with-messages) 可以帮助理解这里所说的 API：它不仅要传递对话内容，还负责把结构化的消息、角色和内容块组织成模型可以处理的输入。它不是模型本身，也不是 GPU 上执行矩阵乘法的推理引擎。迁移的对象是围绕模型工作的服务层。

## 为什么测试通过还不能上线

原有约 700 个集成测试与 Python 实现耦合，迁移后的测试有逾 100 处断言被削弱。2026 年 4 月，Rust 已通过约 98% 的测试，线上输入却仅约四分之一与旧服务一致。另一方面，20 个二元配置项就能产生超过百万种组合，穷举本身并不现实。

这与原文援引的 [Bun 迁移案例](https://bun.com/blog/bun-in-rust) 不同。Bun 创始人 Jarred Sumner 在 2026 年 7 月披露，其 Zig 到 Rust 的迁移对象包含超过 53 万行 Zig 代码，而既有 TypeScript 测试不依赖底层实现语言。Bun 可以让两套实现面对相同的外部测试，并利用 Rust 的编译期内存安全检查发现一类旧有问题。Claude API 的测试却需要随实现一起调整，因而不能只靠测试通过率来判断迁移完成度。

## 让生产环境提供验证信号

影子测试（shadowing）是将实际请求交给两套实现比较行为的做法。[GitHub 早在 2016 年介绍的 Scientist](https://github.blog/developer-skills/application-development/scientist/) 就采用了类似思想：对用户仍返回旧实现的结果，同时执行并观察候选实现，以便在真正切换前发现差异。

Claude API 不能直接重复推理或重复计费。Anthropic 只调用模型一次，将同一输出交给 Rust 重放，并在模型调用前后逐阶段比对。为保护客户隐私，日志只记录差异阶段、位置和长度等指纹，不保留用于排查的请求或回复文本。每隔 10–30 分钟聚合差异，由协调 Agent 分派工作。

## 把验证分成不同速度的反馈环

Agent 在沙箱中合成复现用例，秒级检查后提交修复与回归测试；工程师审核，再由线上流量检验差异是否消失。曾有 Agent 用静态文件补齐搜索工具描述，虽然通过验证，却因没有解决真实服务依赖而被拒绝。审核经验随后转化为共享规则和自动检查，防止其他 Agent 重复走弯路。

Anthropic 的[原始迁移报告](https://www.anthropic.com/research/migrating-api-to-rust)显示，输入一致率曲线最终达到 99.6%，但比较范围在期间有调整。9 月逐步迁移公开流量之后，每请求 CPU 开销下降约 70%，内存开销下降超过 80%，Claude Code 客户请求的首 token 延迟中位数下降约 20%；三个指标的样本范围并不完全相同。服务没有为此停机，也没有冻结功能开发。

## 延伸判断与启示

这个案例对软件工程最大的启发，是重新计算验证的成本。传统的软件重写往往因为实现成本和迁移风险而迟迟无法启动：开发者必须在旧系统上继续交付，又要为新系统投入一批人力。当实现成本下降，工程团队真正稀缺的资源就变成了能够独立判断两个系统是否等价的验证机制。这里可以把项目想象成三个不同的问题：新代码能否编译、能否重现旧代码的业务行为，以及能否在真实流量和真实依赖下稳定运行。三者分别需要编译器、独立的契约测试和生产观测，不能相互代替。如果允许同一个 Agent 同时重写实现和验收标准，却没有外部约束，就等于把考卷和评分标准都交给了答题者。对企业而言，更值得提前建设的是稳定的接口契约、合成数据回放环境、差异分类机制、受控的灰度发布和可回滚的部署系统；这些是可以跨模型复用的资产。尤其对于金融、网络控制面或者其他具有外部副作用的服务，影子执行必须隔离实际写入和计费，同时评估观测数据的隐私风险，不能为了提高验证覆盖率而牺牲生产安全。

从 AI 基础设施的经济性看，也要把 API 服务和模型计算分开。CPU 开销减少 70%，并不意味着整套 AI 推理成本也减少 70%。假设某系统的 API 服务层 CPU 成本只占总请求成本的十分之一，且其他成本保持不变，那么这个环节节省 70% 的直接效果只相当于总成本下降 7%；若请求主要是短输入、短输出但高并发的工具调用，服务层成本占比可能更高，而长上下文、长推理链的任务则可能更受 GPU 计算和内存带宽限制。这是一个用于解释成本结构的假设算例，不是 Anthropic 的真实成本拆分。对于云平台和模型供应商，未来值得跟踪的并不只是模型生成速度，还包括每请求服务成本、队列等待、首 token 延迟的尾部表现、工具调用往返时间，以及系统能否在不中断业务的情况下持续升级。软件工程 Agent 如果能持续降低这些系统改造的门槛，成熟的企业软件和云服务也可能迎来一轮以前因为迁移代价太高而被搁置的基础架构更新。不过，要获得这种收益，先决条件是系统拥有足够可观测、可隔离且能够独立验证的行为边界，而非简单增加 Agent 数量。
