# 长上下文推理的真正瓶颈：稀疏注意力省下的算力，为什么又被索引和显存吃掉？

2026 年 11 月 17 日，Timmy Liu、Nidhi Bhatia、Samkit Jain、Makesh Tarun Chandran 和 Bita Darvish Rouhani 在 NVIDIA Technical Blog 发表了 [Co-Designing Sparse Attention for Efficient Long-Context Inference](https://developer.nvidia.com/blog/co-designing-sparse-attention-for-efficient-long-context-inference/)。原文免费开放，包含实际 GPU 算子测试和近期模型的架构比较。理解这组实验的价值，在于把大模型的长上下文能力从一个产品参数还原成具体的计算、存储与数据搬运问题。

## 从计算账本看稀疏化

假设一个模型需要在 131,072 个历史 token（文本或其他输入的离散编码单元）中查找信息，最终只使用其中 2,048 个位置。核心注意力的候选范围便缩小到原来的六十四分之一，但整个推理过程绝不会因此自动快六十四倍：模型还得先知道应该选哪 2,048 个位置。

这就是索引器（indexer）的作用。它负责为历史位置计算相关性，随后由 Top-k 算子保留得分最高的候选，最后才执行真正的注意力计算。把三部分的耗时记作 T_index、T_select 和 T_attention，再加上其他网络层的耗时 T_other，就能得到一张更有用的性能账本：任何单项加速的收益都必须放进四项之和来衡量。

NVIDIA 对 128K 输入的单层预填充时间进行比较，DeepSeek-R1 的密集注意力占该层时间的 91%；DeepSeek V3.2 的稀疏方案中，索引与筛选合计占 47%，核心注意力占 24%，前馈网络占 25%。这些是不同模型各自的耗时构成，不是两者的绝对速度之比。它们说明，稀疏化改变了工程优化的对象：候选集合虽然变小，寻找候选集合的过程却成了主要负担。

## 同样的算法，为什么有两种截然不同的性能表现？

理解实验的关键是区分 Prefill（预填充，即批量处理输入）与 Decode（解码，即逐步生成输出）。GPU 的性能可以用一个简单的下界理解：执行时间至少受计算量除以计算吞吐率，以及搬运字节数除以存储带宽这两个量约束。哪个量更大，哪个就更可能决定速度。

索引器计算查询向量与历史键向量之间的相关性。预填充时有大量查询，可以组织成较大的矩阵乘法；解码时每一步只有少量新查询，却仍须扫描索引缓存。HBM（高带宽显存）的读取成本因此在后者更加突出。

令 G 表示共享一组键向量的查询头数量。查询头越多，如果能复用已经载入的键，增加的是运算而不是等比例增加的显存流量。实验中，G 扩大 16 倍，解码索引耗时仅变化约 2%。反过来，在查询头总数固定时，把键头数从 1 增至 8，解码耗时达到原来的 7.6 倍。两项数字放在一起看，比单独研究 FLOPs（浮点运算次数）更能解释为什么共享键向量的设计受到欢迎。

这种复用也有硬件上限。推测解码（speculative decoding）先生成候选 token，再由目标模型批量验证。若每次需要处理 D+1 个查询位置，索引器的行数便随 G×(D+1) 增长。矩阵计算块必须装进 Tensor Core 所支持的 tile（计算分块）中；原文测试的 FP32 后处理有效上限约 200 行，FP16 后处理可达 256 行。降低数值精度能减少寄存器压力，但累加结果是否可以使用 FP16，还受数值范围约束。在 G=64、D+1=4 的测试中，两种低精度优化分别达到 1.31 倍和 1.45 倍速度。

向量宽度也是一项资源分配问题。索引头维度从 64 增至 128 时，预填充耗时只达到原来的 1.1—1.2 倍，原因在于矩阵单元与处理打分结果的通用计算单元原本并未达到均衡；解码却要为更宽的键支付更多显存流量。由此便能理解，为什么许多近期稀疏注意力设计把索引头维度设为 128，而不是盲目追求最窄或最宽。

## 两种不同的粒度，决定两张成本账

一条 256K token 的序列，如果索引压缩比为 4，就只需要存储和打分 64K 个索引键。压缩比再提高到 8，参与打分的键又减少一半。这里的压缩并不等于把核心注意力的 KV cache（历史键值缓存）同步缩小；两个结构承担不同职责，可以采用不同设计。

近期模型已有不同的索引组织方式：DeepSeek DSA 采用逐 token 选择，GLM 5.2 在层间共享索引，GLM 5.3 Flash 使用四 token 分组，LongCat LSA-Flash 引入分层检索。它们可以从减少参与评分的候选数这一共同目标来理解，而不是把每一种方法看成完全无关的优化。

另一个容易混淆的变量是最终保留多少位置。Top-k 要在大量分数中寻找少数高分项，因此减少输出集合的大小并不等于免除对输入集合的遍历。原文实验显示，参与评分的键数翻倍时，Top-k 在预填充与解码阶段的耗时分别约增至 1.7 倍和 1.5 倍；而保留数量增加 64 倍，耗时增幅仍小于两倍。

这也解释了两种算子优化的意义。FlashInfer 将评分、归约和筛选放在同一 GPU 算子内，避免把完整的中间分数矩阵先写入显存再读出来；TensorRT-LLM 的 Guess-Verify-Refine Top-k 则利用相邻解码步骤的选择结果通常相近这一性质，在 DeepSeek V3.2 和 V4 的解码测试中达到常规 radix select（基数选择算法）的 2.1—2.4 倍速度。两项结果都是特定算子的改进，不能直接当成整模型的加速比。

索引粒度之外，还有核心注意力的读取粒度。假定每次仍然读取 2,048 个位置，选取 16 个连续的 128-token 块，与选取 64 个 32-token 块相比，理论上需要相同的有效 KV 字节数和注意力运算量。但后者有四倍数量的分块需要组织和合并。原文测得较小分块的预填充与解码耗时分别达到大块方案的约 3.7 倍和 3.5 倍。实际系统因而不能只计算有效字节数，还要计入读取和归并的组织成本。让多个注意力查询头共享同一 KV 头，则能让一次数据读取服务于更多计算。

## 延伸判断与启示

这份测试最适合用来建立模型与推理引擎之间的联合设计思路，而不是直接选出某个最优模型。架构团队可以先确定任务可接受的质量损失，再同时测试索引压缩比、分块粒度、共享头配置以及推测解码接受率。评估指标应覆盖首 token 延迟、后续 token 间隔、并发吞吐、峰值显存和每次成功任务的成本。只报单个算子的加速倍数，或只看长上下文模型在某个检索基准上的正确率，都不足以说明服务端真正获得了什么。尤其是代码智能体，遗漏一处关键依赖可能导致整条任务失败，省下的 token 成本也可能被重新尝试抵消。

从硬件竞争角度看，随着核心注意力的计算量被稀疏化压缩，索引缓存的带宽利用率、片上存储、矩阵单元与通用计算单元之间的配合，以及编译器和算子融合能力，可能成为更有区分度的竞争指标。但这取决于稀疏模型能否在真实长上下文任务中维持质量，以及索引优化能否在生产批量和延迟约束下保持收益。单凭 NVIDIA 自身硬件的微基准，不能得出 GPU、ASIC 或其他加速器的全面成本排名。真正应该追踪的是，在同等任务成功率和服务质量下，系统能以多少实际资源完成一次有用的推理。
