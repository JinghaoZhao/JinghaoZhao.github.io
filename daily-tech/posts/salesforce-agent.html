我今天选择它，是因为它回答了一个比“GPT-6 和 Claude Opus 谁更聪明”更有商业价值的问题：

为什么模型越来越强，企业却依然很难放心让 AI Agent 直接操作自己的业务系统？

Salesforce 给出的答案很有意思：问题不一定在模型能力，而在系统架构。

早期 Agentforce 把业务规则、用户身份、数据检索、权限控制和任务执行要求全部塞进一个巨大的 Prompt，希望大模型同时做好所有事情。

结果，当规则变多以后，模型会遗漏部分指令。

对于普通聊天机器人，这可能只是一次回答不准确。但如果 Agent 正在操作患者数据、修改客户记录或者执行财务流程，遗漏一条规则就可能造成严重后果。

Salesforce 最终选择了一条与纯 Agent 自主决策不同的路线：把可以确定的事情交给传统代码，把真正需要判断的事情交给大模型。

更重要的是，它把身份管理、数据整合、上下文选择和工具调用分别做成独立基础设施，而不是要求模型依靠 Prompt 自觉遵守。

这篇文章最大的价值，是展示了当 AI Agent 从 Demo 进入企业生产环境后，软件架构正在发生怎样的变化。

以下按可靠性、数据、权限和平台经济学重新组织原文论证，并使用 Salesforce 官方技术文档与财报交叉验证。最后补充这种架构对企业软件市场和 CRM 等投资标的的意义。

Salesforce 已经拥有数十亿次 Agent 工作记录，但真正困难的是让每一次操作都可靠

截至截至 2026 年 7 月 31 日的 Salesforce FY2027 第二财季，公司披露 Agentforce 与 Slack 累计完成 70 亿个 Agentic Work Units（AWU）。

其中，仅第二财季就产生了 32 亿个 AWU，比上一季度增长约 97%。

AWU 是 Salesforce 自己定义的工作量单位，用于衡量 Agent 在生产环境中完成的离散操作，例如处理客户工单、更新记录或触发自动化流程。

这个数字不能直接解释成 AI 取代了 70 亿次人类劳动，因为不同 AWU 的复杂度和经济价值可能相差很大。但它至少说明，Salesforce 已经能够在实际企业系统中观察到大规模的 Agent 操作。

其同期财报还披露，Agentforce 的年度经常性收入（ARR）超过 15 亿美元，同比增长超过 240%；Agentforce 与 Data 360 合计 ARR 接近 39 亿美元。需要注意，Agentforce ARR 的统计口径在该季度纳入了 Slackbot 和 Headless 360，因此同比增长不完全代表同一产品范围下的自然增长。Salesforce Investor Relations

这种部署规模让 Salesforce 遇到了实验室 Agent 很少暴露的问题。

一个 Demo 可以只处理少数固定任务。

但真正的企业系统可能同时拥有客户数据、业务审批、复杂权限、第三方应用以及不断变化的内部制度。

例如，一家医疗服务公司希望通过 Agent 帮患者查询预约。

看起来只是一个简单问题。

但 Agent 必须先确认用户是谁，找到正确的患者记录，读取有权限访问的预约信息，并避免泄露其他患者的数据。

如果用户随后要求更改保险计划，Agent 还需要判断是否满足业务条件，以及哪些操作需要额外确认。

这些步骤并不是都需要语言理解。

其中相当多的部分应该遵循严格的业务规则。

而把它们全部写进 Prompt，恰恰是 Salesforce 早期遇到的架构问题。ByteByteGo

企业 Agent 最危险的设计，可能就是一个写得非常完整的 System Prompt

文章介绍，第一代 Agentforce 使用的是一种非常直观的架构。

开发者把业务说明、限制条件、工具描述和相关数据集中放入模型上下文。

例如，医疗客服 Agent 的 Prompt 可能告诉模型，回答患者问题前必须先查询预约记录，不能讨论不属于当前患者的数据，某些操作只能在满足特定条件后执行。

这种设计的优点是开发速度快。

企业不需要为每个工作流程编写复杂代码，只需要用自然语言说明要求。

但是，模型对这些指令的执行并没有传统程序那样的确定性。

Krishnaprasad 在采访中回忆，早期 Agentforce 面对少量规则时表现不错，但随着团队不断添加限制，模型开始忽略部分要求。他提到，在当时的系统中，超过大约八条指令后，这种现象就明显出现。

这里需要一个重要限定。

八条指令不是所有大模型共同具有的硬性上限。

这是 Salesforce 在特定早期系统中观察到的工程现象。不同模型、不同任务、不同指令复杂度都会影响结果。

但更广泛的研究确实支持同一个方向。

IFScale 是一个专门测试大模型能否同时遵守大量指令的 Benchmark。

其公开测试让模型在一个 Prompt 中处理最多 500 条简单指令。

在该测试覆盖的模型中，表现最好的 Gemini 2.5 Pro Preview 在 500 条指令下的遵循率约为 68.9%。

需要强调，该榜单采用的是较早一代模型，不能据此推断 2026 年 11 月前沿模型仍然只有这个水平。但它说明，长上下文容量并不自动等于可靠的多约束执行能力。Distylai

这是一个很重要的技术区别。

模型能够读取一百万 Token，不代表它能够像程序一样保证执行其中每条约束。

从模型角度看，许多自然语言规则仍然是需要解释和遵循的上下文，而不是由运行环境强制实施的安全机制。

假设一家银行规定，任何超过某个金额的转账都必须经过人工审批。

如果这条要求仅仅写在 Prompt 里，那么系统实际上是在期待模型每次都记得检查。

但银行真正需要的是，即使模型误解了指令、遗漏了检查，交易系统本身也不能允许违规转账。

因此，Salesforce 逐渐形成了一个更明确的架构原则：

需要绝对执行的业务规则，不应该只存在于模型的自然语言指令中。

Salesforce 的解决方案：把大模型重新放回一个由代码控制的执行系统里

文章最重要的技术设计，是 Agent Script。

这是一种用于描述 Agent 行为的专用语言（Domain-Specific Language，简称 DSL）。

开发人员可以用接近 Python 的形式描述 Agent 的行为，但它不只是另一种 Prompt 模板。

Agent Script 可以同时包含确定性的逻辑，以及交给大模型处理的自然语言指令。

两者在运行时有明确区别。

例如，某个操作必须先查询数据库，再检查结果是否为空，然后才能进入下一步。

开发者可以把这些要求写成代码。

运行引擎按照程序逻辑执行，不需要模型判断是否应该遵守。

如果某个步骤需要理解用户含糊的表达，或者根据大量文字信息作出判断，系统才调用 LLM。

Salesforce 的官方架构文档证实了这一设计：Agent Script 先被编译为一种称作 Agent Graph 的执行表示，再由 Atlas Reasoning Engine 负责运行。Atlas 实际上是一种能够处理确定性操作与模型推理的状态机执行器。Architect

这听起来像是给 Agent 增加了一层工作流引擎，但关键区别在于，工作流并不需要完全固定。

模型仍然能够理解用户目标、选择某些任务路径并生成回答。

只是系统不再允许模型拥有所有控制权。

文章举了一个医疗预约查询的例子。

假设患者 Harper Clark 问：“我下次和 Perl 医生的预约是什么时候？”

在旧架构中，开发者会在 Prompt 中写下“回答前必须查询预约”。

然后希望模型执行。

在新架构中，预约查询会被放入相应子 Agent 的 before_reasoning 逻辑中。

当执行流程进入这个子 Agent，系统会先运行查询代码，再把结果提供给模型。

因此，模型不再需要判断是否应该调用预约工具。

它只需要根据已经获取的数据理解问题并生成回答。

这实际上减少了模型需要处理的决策数量。

可靠性的提升并不完全来自模型更聪明，而是来自系统不再要求模型决定每一个步骤。 ByteByteGo

Agent Script 还有一个工程细节：确定性执行不等于可以忽略运行时语义

Salesforce 官方技术文档提供了一个比文章主体更深入的细节。

Agent Script 中的 before_reasoning 并不一定只在每次用户提出新问题时执行一次。

Atlas 使用的基本执行单位是一次 parse，即对子 Agent 的一次完整处理过程。

进入子 Agent、完成工具调用后继续处理，以及同一子 Agent 收到新用户消息时，都可能触发新的 parse。

因此，一次用户请求可能导致 before_reasoning 执行多次。

这意味着，开发者不能简单地把所有操作都塞进这个阶段。

如果某段代码只是读取数据，重复执行通常可以接受。

但如果它会创建订单、发送邮件或者修改记录，重复执行可能产生副作用。

因此，对可能重复触发的操作，需要使用幂等性设计（Idempotency）。

所谓幂等性，就是同一个操作即使重复执行，也不会产生额外的业务结果。

例如，一个带有唯一请求 ID 的订单创建接口，可以在收到重复请求时返回已有订单，而不是创建第二笔订单。

Salesforce 还提醒，某些运行路径可能提前结束推理循环，使 after_reasoning 不会执行。因此，即使是确定性代码，也必须理解运行时的生命周期和异常分支，不能想当然地假设每条路径都会经过所有阶段。Architect

这点特别值得工程团队注意。

用代码替代 Prompt，只是把可靠性问题转化成了更熟悉的软件工程问题，并没有让错误自动消失。

但这是有价值的转化。

因为传统软件已经发展出大量成熟方法，可以测试状态机、验证权限、处理重复请求和审计执行过程。

相较于试图从模型输出中推断某条指令有没有被遵守，这些机制更容易获得明确的工程保证。

企业 Agent 的另一大难题：同一个客户可能在五个系统中拥有五种身份

文章随后进入 Salesforce 最重要的传统优势领域：企业数据。

即使 Agent 能够可靠执行工作流程，它仍然需要知道自己正在处理谁的数据。

假设一名患者在 CRM 系统中使用完整姓名登记。

在保险系统中，她可能只有一个内部客户编号。

在预约系统中，她可能使用缩写姓名。

在 Snowflake 数据仓库里，她的电话又可能采用不同格式。

对于人类员工，这些差异可以通过经验和交叉查询解决。

但如果企业把所有记录直接交给模型，让它自行判断哪些属于同一个人，就会引入新的错误来源。

模型可能错误地合并两个不同的人。

也可能无法识别两个实际上属于同一人的记录。

如果涉及医疗、金融或其他敏感信息，这种错误甚至可能导致严重的隐私泄露。

Salesforce 因此把身份整合放在独立的数据基础设施中，而不是交给模型推理。

这套系统被称为 Data 360。ByteByteGo

Data 360 首先连接企业原有的数据源。

企业不需要把所有数据都迁移进 Salesforce 的一张巨大数据库。

在支持的连接方式下，Data 360 可以从外部系统读取数据，并建立统一的数据视图。

文章采访中的演示使用了 Snowflake。Krishnaprasad 修改了一位模拟患者在 Snowflake 中的保险信息，演示里的统一资料随即反映了变化。

这说明数据整合层能够与外部系统保持连接，但不能因此推断所有连接器在任何部署条件下都具有零延迟的一致性。

随后，Data 360 将不同系统的数据映射到共同的数据模型。

例如，一个系统把姓名存成单个字段，另一个系统拆分为名和姓。

系统可以通过数据模型转换，让这些字段在统一视图中具有一致含义。

最后是 Identity Resolution，也就是身份解析。

管理员可以配置精确匹配、模糊匹配以及标准化匹配等规则。

例如，电话号码中是否包含国家代码、空格或分隔符，不应该自动导致两条记录被识别成不同的人。

这些规则的输出，是一个连接不同原始记录的统一客户视图。

文章强调，底层来源记录并不会因为创建统一客户资料而被直接改写。

这一点对企业尤其重要，因为 Salesforce 不是要取代所有企业数据库，而是希望在现有数据系统之上建立一个能够被 Agent 使用的统一数据层。ByteByteGo

真正的 Context Engineering，并不是给模型更大的上下文窗口

这部分是我认为文章最值得深入理解的地方。

大模型的上下文窗口越来越大。

但 Salesforce 发现，企业 Agent 不应该因此把所有可访问的信息全部塞进 Prompt。

原因不仅是 Token 成本。

大量不相关信息还会降低模型找到关键事实的效率，并增加错误理解或泄露数据的风险。

假设用户询问保险计划的具体条款。

如果系统把客户全部交易记录、历史咨询、公司内部文档以及相关产品资料一股脑加入 Prompt，模型需要在大量信息中寻找真正相关的内容。

而更合理的方案是，在调用模型以前就完成数据筛选。

Salesforce 为此开发了 Agent Context Engine（ACE）。

它不是单纯的向量数据库，也不只是一个 RAG 检索组件。

它负责识别当前任务需要哪些信息，选择数据源，处理搜索结果，应用权限与隐私规则，再把整理后的上下文提供给模型。

文章介绍，ACE 会综合考虑用户身份、Agent 身份、当前任务、相关实体、信息权威性以及新鲜程度。

例如，如果用户询问的是已经生效的保险计划，系统应该优先使用经过确认的正式记录，而不是某次聊天中提到的计划草案。

这种机制要求上下文系统区分不同信息的可信程度，而不只是寻找语义最相似的文本。ByteByteGo

Salesforce 在采访中展示了一组非常有意思的数据。

对于一个保险计划查询任务，没有独立上下文管理的 Agent 使用了约 124,000 个 Token。

采用 ACE 后，相同问题只需要约 9,000 个 Token。

也就是说，这个演示中的上下文规模减少了约 93%。

当用户继续追问搬到佛罗里达州以后应该如何调整保险计划时，差异进一步显现。

在旧方案中，两个问题累计使用约 300,000 个 Token。

使用 ACE 的方案则在包含后续保险登记操作的三个处理步骤中，累计使用约 65,000 个 Token。

这里的后一组数字并不是完全相同工作量下的严格 Benchmark，因为两个流程包含的步骤不同。

但它足以展示一种可能的工程优势：通过有目的地筛选上下文，可以显著减少无关信息的传递。ByteByteGo

这种优化对 Agent 具有比普通聊天更加重要的意义。

Agent 往往需要多次调用模型。

每次调用都可能携带历史记录、工具结果和系统指令。

如果每个步骤都重复传递大量信息，那么随着任务链条延长，Token 消耗和推理延迟可能迅速增加。

但如果系统能够维护结构化状态，只向模型提供当前步骤需要的信息，就可能显著降低长期执行成本。

ACE 不只是检索系统，它还决定什么信息值得成为长期记忆

文章举了一个很容易被忽视的例子。

用户告诉保险 Agent，自己可能搬去佛罗里达州。

这句话并不等于搬家已经发生。

系统可以把它记录为一个待确认意向，但不能立即把客户的永久居住州改成佛罗里达。

只有当用户实际完成相应的保险登记或资料更新以后，某些信息才可能成为正式业务事实。

Krishnaprasad 在演示中强调了这种区别。

一次对话中的陈述，可能只是临时状态或用户意图。

经过正式业务流程确认的信息，才适合进入权威记录。

所以 ACE 不仅管理上下文，还需要决定哪些信息应该被保留，以及保留以后应当具有什么状态。ByteByteGo

这让我想到企业 Agent 与个人 Chatbot 的一个本质区别。

个人助手记住你正在考虑买一辆车，即使后来发现你没有购买，通常也只需要更新偏好。

但企业 Agent 如果把客户的意向误认为已经执行的业务事实，就可能影响计费、合同、库存或监管记录。

因此，企业级 Agent 的记忆不应该只是聊天历史的压缩版本，而应该与正式业务状态和数据来源保持明确关系。

这是我基于文章技术设计得出的延伸判断，而不是 Salesforce 已经证明的一条通用行业定律。

Agent Identity：为什么 AI 不能直接继承用户的全部权限？

接下来是另一项非常重要的设计。

许多早期 Agent 系统使用用户自己的凭证执行操作。

例如，销售人员 Alex 将自己的 Salesforce 账户连接到 Agent。

如果 Agent 直接使用 Alex 的授权，那么它理论上能够执行 Alex 账户权限范围内的操作。

但这里存在一个被严重低估的问题：

人类拥有某项权限，不意味着代表这个人工作的 AI 应该拥有同样的权限。

例如，Alex 可能有权限批量修改客户记录。

但他只是让 Agent 总结本周销售机会，并没有授权它批量修改所有客户资料。

如果 Agent 直接继承 Alex 的完整权限，那么模型发生错误时，就可能执行远超任务需要的操作。

而且 AI 的行为速度远高于人工操作。

一个员工手动错误修改几条记录，往往还有机会及时发现。

但一个自动化 Agent 可能在很短时间里重复执行大量错误操作。

Salesforce 因此引入 Agent Identity。

在这种设计下，Agent 不再只是借用用户账户。

系统同时保留用户身份与 Agent 自身身份，并针对每个身份配置权限。

文章介绍，Agent 进行身份验证时会涉及用户与 Agent 各自的令牌。

真正执行操作以前，系统需要检查用户权限、Agent 权限以及适用的数据访问政策。

只有相关检查都允许，操作才能继续。ByteByteGo

例如，Alex 可能有权查看和修改销售机会。

但如果他的研究 Agent 只被授予读取权限，那么这个 Agent 就不能因为模型决定“最好顺便更新一下记录”，而自动获得写入能力。

这种设计实际上把传统 IAM（Identity and Access Management，身份与访问管理）原则扩展到了 AI Agent。

它不要求 Agent 永远作出正确判断。

它要求 Agent 即使判断错误，也无法绕过系统设置的权限边界。

当然，权限检查仍然不是完整的安全保证。

如果 Agent 本来就被允许修改某种记录，却错误地连续修改一万次，那么单次操作的权限验证可能全部通过。

这意味着企业仍然需要速率限制、操作数量限制、异常检测和高风险操作审批等配套机制。

Salesforce 官方关于 Agent Fabric 的资料也介绍了 Trusted Agent Identity 和针对高风险操作的人类验证机制，但这些能力是否覆盖每个 Agentforce 部署，还要取决于具体产品与配置。Salesforce

企业软件正在发生另一种变化：Agent 不一定需要打开 Salesforce

文章最后从 Agent 的内部架构转向软件平台战略。

过去使用 Salesforce，通常意味着员工打开 Salesforce 的网页或者应用界面。

销售人员进入 CRM。

客服进入 Service Cloud。

管理员使用后台工具。

但 AI Agent 并不一定需要这些界面。

它可能运行在 Slack、Claude 或其他工作环境中。

用户也可能根本不想知道底层数据来自哪个企业软件。

例如，一名销售经理在 Slack 里询问：

“过去一百天最值得跟进的二十个销售机会是什么？”

从用户角度看，他只希望获得结果。

Agent 需要访问客户数据、运行查询、按照规则排序，再返回答案。

并不需要让用户手动打开 CRM，点击多个菜单。

Salesforce 把这种设计称为 Headless，也就是将底层系统的功能与传统用户界面分离。

公司在 2026 年 4 月发布 Headless 360 时，就明确提出要把 Salesforce 的能力通过 API、MCP 工具和命令行接口开放给 Agent。

这意味着 Salesforce 希望继续控制底层数据和业务逻辑，却不再要求每一次用户操作都发生在自己的界面里。Salesforce

这是一项非常重要的商业模式变化。

传统 SaaS 产品通常把用户界面当作最重要的客户接触点。

但在 Agent 时代，最终用户可能只接触 AI 助手。

底层软件则负责提供数据、权限和可执行能力。

如果这种趋势持续，企业软件的竞争将不再只是哪个产品拥有更好用的界面。

还包括哪个平台能够让外部 Agent 更容易、安全地使用自己的能力。

MCP 解决工具连接问题，但又产生了一个新问题：工具太多怎么办？

Salesforce 为外部 Agent 提供能力时，采用了 API、Skills 和 MCP 等机制。

它们各自解决不同问题。

API 定义某个系统可以执行什么操作。

例如，查询客户资料、创建销售机会或者更新订单。

Skill 则告诉 Agent，完成某种较复杂任务时应该如何组合这些操作。

比如，执行一个销售分析任务，可能需要先查询记录，再按条件过滤，最后调用某个分析接口。

MCP（Model Context Protocol）则提供一种标准化方式，让 AI Agent 发现并调用外部工具。

问题是，当企业拥有数百甚至数千个可用工具时，直接把所有工具的定义放入模型上下文会非常昂贵。

每个工具都需要名称、说明和参数定义。

如果模型每次调用都必须读取数百个工具的 Schema，不仅浪费 Token，还增加工具选择难度。

Salesforce 因此在自己的 MCP Server 中使用了工具发现机制。

文章介绍，这个接口只需要向模型暴露四个基础工具定义。

当 Agent 需要执行任务时，先搜索可能相关的能力。

找到候选工具以后，再读取具体调用规范。

最后由执行层把请求发送到正确的系统接口。

以刚才的销售机会查询为例，Agent 可以先通过 discover 查找合适能力，再通过 describe 获取具体操作要求，最后通过 dispatch 执行请求。

这种设计不需要模型事先知道整个 Salesforce 平台上的所有 API。

它只需要具备发现并理解当前任务所需工具的能力。ByteByteGo

从系统设计角度看，这与现代软件工程中使用服务发现或动态加载能力有些相似。

程序不需要把整个企业服务目录预先加载到每一次请求中。

它可以根据当前需求动态找到对应服务。

因此，MCP 真正大规模进入企业后，可能需要的不只是一个工具调用协议，还包括工具目录、语义发现、权限检查、调用审计和版本管理等基础设施。

Salesforce 最终想建立的，不只是 Agentforce，而是企业 Agent 的统一运行环境

文章最后提到了 Salesforce 的一个长期方向：Enterprise AI Harness。

可以把 Harness 理解成 Agent 的运行与管理框架。

它不是一个特定大模型，也不只是一个聊天机器人界面。

它希望把企业 Agent 所需的数据访问、工具执行、身份管理、运行追踪和评测能力整合起来。

企业可以使用 Salesforce 自己的 Agent。

也可以使用其他平台提供的 Agent。

但底层业务数据、权限和可执行流程仍然能够通过统一平台进行管理。

文章引用两位 Salesforce 高管的判断，认为企业最终希望获得的是一套跨 Agent 平台通用的运行基础设施，而不必在每种模型或 Agent 产品中重复建设这些能力。

不过，需要区分技术愿景和已经完成的产品。

文章介绍了 Salesforce 已经实现的多个组件，但没有证明所有企业都已经能够使用一套完全统一、没有配置复杂度的 Harness。

统一不同供应商的 Agent、权限和审计体系，本身仍然是一项复杂的软件工程任务。ByteByteGo

这也是 Salesforce 战略中非常值得关注的地方。

它并没有试图证明自己的基础模型一定比 OpenAI、Anthropic 或 Google 更强。

它更强调，企业真正拥有价值的数据和业务流程，已经存在于 Salesforce 及其连接的系统中。

如果企业可以自由替换前端模型，却始终需要 Salesforce 提供可靠的数据与工作流，那么 Salesforce 就可能在 AI 时代继续保持重要地位。

但反过来，如果其他平台能够更便宜、更灵活地提供相同能力，Salesforce 也可能面临新的竞争。

因此，Headless 战略既是机会，也意味着它愿意减少对自有用户界面的依赖。

我的理解：企业 Agent 正在从 Prompt Engineering 进入 Software Architecture 阶段

以下是我的延伸分析，不属于 ByteByteGo 或 Salesforce 已经直接证明的结论。

我认为这篇文章最重要的启示，是企业级 AI Agent 的核心竞争力正在从“写出更好的 Prompt”，转向“设计更可靠的执行系统”。

过去开发 Agent，团队往往把大量精力花在提示词调试上。

当模型遗漏某项要求时，开发者就增加新的系统指令。

当模型错误调用工具时，就再补充几条工具使用规则。

可是，当 Agent 开始真正接触业务系统，这种方法会越来越难以维护。

因为业务规则本身往往具有非常明确的逻辑。

权限应该由授权系统执行。

数据身份应该由可信的数据管理系统解析。

上下文应该由检索和筛选系统准备。

模型则应该专注于那些无法方便地通过固定规则表达的理解和判断任务。

这并不是否定大模型的重要性。

恰恰相反，模型越强，越可能承担复杂任务，企业就越需要能够约束其行为边界的运行基础设施。

我认为未来优秀的 Agent 系统，不应该完全依赖模型持续作出正确决定，而应该尽量让模型只承担真正需要智能判断的部分。

其余工作交给传统软件系统，可以降低错误概率、成本和调试难度。

这也意味着，Agent 时代并没有让传统软件工程知识过时。

分布式系统、状态机、数据库、身份管理、幂等性、审计日志和访问控制，反而可能成为构建可靠 AI 产品最重要的基础能力。

对 SaaS、云和网络安全公司的投资含义

这篇文章也给了一个很有价值的企业软件投资框架。

过去市场担心 AI 会直接取代 SaaS：用户不再需要复杂的 CRM 或项目管理界面，只需要告诉 Agent 自己想做什么。

这种担忧有合理基础。

但 Salesforce 的架构展示了另一种可能：AI 可以取代部分用户界面，却不一定能够轻易取代底层业务系统。

企业仍然需要可靠地保存客户记录。

仍然需要管理业务权限。

仍然需要执行合同、审批和工作流程。

仍然需要连接不同数据库，并保留可审计的操作历史。

因此，真正需要重新估值的，不是“所有 SaaS 都会消失”，而是 SaaS 价值链中哪些部分容易被 Agent 替代，哪些部分仍然具有稀缺性。

对于 Salesforce，最值得观察的可能不是 Agentforce 每个月执行多少 AWU，而是这些操作最终能否带动可持续的收入增长。

截至最新披露的 FY2027 第二季度，Agentforce ARR 已超过 15 亿美元，但 Salesforce 整体季度营收为 113 亿美元，同比增长约 11%，其中还包含 Informatica 并购贡献。

这说明 AI 产品正在形成有意义的业务规模，但其增长尚不能直接等同于整个公司的有机增长重新加速。Salesforce Investor Relations

对于 MSFT、GOOGL、AMZN 等平台型公司，我认为需要关注谁能成为 Agent 的默认身份、工具和数据访问层。

如果企业允许不同模型和 Agent 进入内部系统，那么权限管理、API Gateway、工具发现、日志和数据治理，都可能成为反复使用的核心服务。

对于 CRWD、ZS、PANW 等安全厂商，这种架构也提示了潜在机会。

Agent 可能在短时间内执行大量操作，而且能够跨多个系统自动工作。

这会提高企业对身份治理、异常行为检测和最小权限控制的需求。

但这种需求能否转化成现有安全厂商的收入，还取决于这些能力由安全平台、云厂商还是企业应用提供商来实现。

因此，不能仅仅因为 Agent 使用量增长，就认为所有网络安全公司的定价能力都会同步提高。

最后的判断：未来最好的 Agent 系统，可能恰恰是不让大模型拥有太多控制权的系统

我认为《A Deep Dive into Salesforce’s Agent Tech Stack》值得记住的，不是 Salesforce 开发了多少新的产品名称，而是它揭示的一条工程规律。

当 AI Agent 进入真实企业环境，可靠性不能只依靠模型自己的判断，而必须建立在能够被验证和执行的系统约束之上。

过去 AI 应用的主要挑战，是让模型完成原本做不到的任务。

未来企业级 AI 的主要挑战，可能是让模型能够持续完成任务，同时不越权、不误操作、不浪费大量计算资源，并且在失败时能够被发现、恢复和审计。

Salesforce 的设计把这一挑战拆解为传统代码、数据整合、上下文管理、独立身份和动态工具调用等工程问题。

这不意味着所有问题都已经解决。

但是，它指出了一条非常有希望的商业化路径：不要期待一个越来越聪明的模型自动理解企业所有复杂制度，而是让企业现有的软件基础设施明确告诉模型，它可以看到什么、可以决定什么，以及绝对不能做什么。

Agent 时代真正成熟的标志，也许不是 AI 可以独立完成越来越长的任务，而是企业终于能够放心让它完成这些任务。
