# AI 没有只是优化 CPU，它重新发明了计算的组织方式：Frostbite 的 4.59 倍能效意味着什么？

2026 年 11 月 18 日，芯片研发公司 Architect Labs 发表了一篇免费公开的技术长文 [《Introducing Frostbite: A new CPU architecture discovered, designed, and verified end-to-end by AI》](https://architectlabs.com/blog/frostbite)，署名为 Architect Labs 研究团队。它尝试回答一个比“AI 能不能帮工程师写 RTL”更难的问题：如果把编程语言、指令集、任务调度和芯片物理设计放进同一个自动探索系统，AI 能否找到一种传统 CPU 不会自然走向的计算架构？Frostbite 的初步答案颇具冲击力：在团队选定的 25 项工作负载和一个特定的传统 CPU 核心基准上，它报告了 **4.59 倍的每瓦性能和 8.77 倍的单位面积性能**。这些仍是流片前的设计评估，而非上市芯片的实测成绩。真正值得花十五分钟理解的，不只是倍数，而是它改变了什么，以及那些倍数究竟是在什么条件下得到的。

## CPU 为什么把大量资源花在寻找原本存在的并行性上

程序员写的代码包含计算顺序，也包含数据之间的真实依赖。两条指令如果要读写同一份状态，执行次序就很重要；若它们互不依赖，理论上可以同时进行。传统通用处理器面对的是一种保守的编程模型：指令可能修改共享内存，硬件必须通过取指、译码、发射、流水线控制以及各种依赖检查，尽可能挖掘本来潜藏在程序里的并行机会。设计越想加快单核性能，就越需要复杂的硬件机制来猜测、追踪或安排这些依赖。

多个 CPU 核心之间还有另一笔开销。它们通常需要维持共享内存的可理解语义，靠各级缓存和一致性协议让不同核心观察到的数据尽量协调。缓存既是性能关键，也消耗面积和电能。一旦工作规模扩大，光是把数据送到对的地方、确保版本正确，就可能变成比算术运算更困难的事情。传统架构当然不是静止不变，但 Architect Labs 选择质疑的是它背后的假设：程序必须先丢失某些依赖信息，再让硬件以高昂代价将它们重新找回来吗？

Frostbite 将这个问题向编程模型的上游移动。它不是单纯修改 RISC-V 核心、给缓存增加一层，或使用更激进的乱序执行单元；它首先重新定义程序如何表达计算，接着让编译器、指令集和执行单元沿着这个表达方式一起变化。这也是该项目与该公司此前 [Redwood AI 推理加速器](https://architectlabs.com/blog/redwood) 的区别：Redwood 着重展示 AI 如何按既定任务快速生成并验证一整套芯片系统，Frostbite 则让自动化系统参与更上游的架构选择。

## 用“交互网”保留依赖，而不是事后找回依赖

Frostbite 使用的理论基础叫交互网（interaction nets），这不是 2026 年才出现的技术。Yves Lafont 在 1990 年的[经典论文](https://doi.org/10.1145/96709.96718)中已经提出这一计算模型。程序不再主要表现为共享变量上的命令序列，而被表示为相互连接的节点。一次计算发生在满足条件的一对相连节点之间，系统通过局部重写改变这张图。每次重写影响有限的邻域，独立的重写可以以不同顺序发生。

这种模型最重要的约束是线性使用：每个值有明确的拥有关系，复制、转交和消费不能依赖一块随意共享且可变的全局状态。把状态的所有权和数据依赖写进程序表示后，硬件获得了一份更明确的执行地图。它不必像传统通用核心那样，从一串可能相互冲突的操作中重新猜测哪些工作能够同时开始。

研究团队用五皇后搜索说明这种差异。普通的顺序程序可以逐层尝试棋盘布局；交互网则直接暴露不同分支之间的独立性。在他们展示的例子中，总共需要 3,183 次交互，但最长依赖链只有 262 步，平均每一步约有 12 个交互同时处于可执行状态。总工作量并没有凭空消失，改变的是在足够多计算资源可用时，这些工作能被多大程度地重叠执行。因此“并行性免费”并不意味着通信、调度和硬件容量免费，而是说程序表示本身保存了可并行的结构，不必再额外依靠传统线程、锁或复杂乱序逻辑来恢复。

配套的软件入口是 [Vine 编程语言](https://vine.dev/)。它给程序员提供接近常规高级语言的写法，再把程序编译成包含交互网信息的中间表示 Ivy。编译器尝试预先化简可以静态确定的部分，留下数据、计算节点与控制节点组成的网络。外观看起来固定的图，运行时仍可能因为递归、条件分支和不断产生的新任务而呈现高度动态的并行行为。这也是最初的朴素实现不够快、需要重新设计专用运行机制的原因。

## 真正新颖的地方，是把任务调度变成空间中的硬件行为

Frostbite 由许多小型 tile（计算瓦片）连接而成。一个 tile 既有实际执行计算的引擎，也有本地存储、运行时管理和网络接口；多块 tile 组合成更大的计算区域。这里的关键，不是把传统 CPU 核心复制很多份，而是将任务所有权、局部数据和任务迁移尽可能放在物理上相邻的位置。

编译器先把程序拆为短小的可运行片段。一个片段只要输入齐备，就能在执行引擎中持续跑完。如果它碰到递归或分支，生成了执行规模暂时未知的新工作，尚需等待的后续部分会被存成一条本地记录，由 frame manager（执行帧管理器）追踪。可立即开展的新任务进入硬件工作队列，当前 tile 拿走最新任务继续执行，剩下的任务可以由空闲邻居通过片上网络领取。

这种机制就是工作窃取（work stealing），但它不依赖一个集中式调度器持续给所有执行单元分配工作。一个 tile 优先执行自己的任务；没有任务时向附近有余量的 tile 请求；仍然没有任务就进入休眠，减少活动功耗。当多个分支在不同 tile 上完成，返回消息会更新等待记录的计数，最后一个必要结果抵达时，后续计算自动被唤醒。任务可能以不同顺序完成，依赖关系却仍然由程序结构约束。

五皇后例子在物理芯片上的展开因此十分直观：一块 tile 探索棋盘的某个状态，产生若干可能的下一步；它自己继续其中一条路径，邻居接走其余路径，空闲的 tile 则暂时睡眠。研究团队表示，具体的工作传播机制并非由人预先逐条写死，而是在性能回归测试与局部搜索中由 AI 系统形成。这里的“自主发现”指的是在人工选定的目标、编程模型、验证框架和优化指标之内找到实现规则，并不等于无人设定研究目标。

这种架构把一部分原来交给操作系统、运行时库或复杂 CPU 发射机制的职责推到了片上的局部网络。它节约了一些集中控制的成本，却必须付出新成本：tile 之间传递任务、维护等待状态，以及管理网络流量。后面的能耗分析恰好展示了这些开销的转移，而不是宣称它们消失。

## 如果 AI 能同时改语言、架构和电路，设计流程会发生什么

传统芯片开发往往沿着较长的交接链条前进：需求变成文字架构说明，架构师定义指令与模块，设计工程师写 RTL（寄存器传输级硬件描述），验证团队建立测试，物理设计团队再确认面积、时序与功耗。任何前面阶段的变更都可能牵动后面数个环节。为了避免不断返工，项目不得不较早冻结某些决定；而这种冻结又让软件与硬件之间的深层联合优化变得困难。

Architect Labs 让多组 AI agent 同时探索不同候选方案。开始时，人类明确希望新架构擅长哪些计算模式：高度并行、分阶段推进、长串行链、数据依赖分支和递归。研究团队设置了 25 项工作负载，其中 10 项用于探索与调优，15 项作为保留的最终评价集。工作负载包括矩阵乘法、卷积、加密、稀疏运算、排序、图搜索、JSON、Huffman 编码和递归问题；后来又在评价集中加入 Kalman 滤波、主成分分析、有限元分析、LU 求解和 LZ4 解压等更实用的任务。部分基于 SPLASH-2 的测试核被缩小到常规规模的六十四分之一，以便加快探索；这会影响最终性能数字能否外推到实际大数据集。

agent 先综合研究文献、既有基准和 Python 性能模型，选出架构方向，形成一份 141 页的初始设计材料。令人印象深刻的并不是这份材料的页数，而是它随后被舍弃：第一轮 RTL 形成后，早期材料中的许多估计与真实物理约束严重不符，再让未经修正的文字说明统治后续设计，反而会把错误稳定地传递下去。

团队于是建立了 ASL，一种自有的可机器检查规范语言，并用它描述名为 Arcmodel 的系统模型。普通自然语言能解释设计意图，却难以无歧义地指定每个状态转换、协议和边界条件，也无法确保大量 agent 在不同分支上写出的东西彼此兼容。ASL 把相关约束写成可验证的“契约”，允许宏观协议与微观流水线同时进入同一个检查体系。它可以描述内存顺序、控制状态寄存器、仲裁、计算函数、连线行为等，还能转换为 [Lean 证明系统](https://lean-lang.org/)使用的表示，让不同层级的设计在共同规则下比较。

Frostbite 最后拥有覆盖 31 个芯片模块的契约网络；团队称由 ASL 展开得到的 Lean 表示超过 80 万行。数量本身当然不等于整颗芯片的商业级可靠性，但有了统一、可检查的语义约束，agent 才能在修改编译器、指令集、系统模型、RTL 和验证材料时知道什么不可被破坏。这也降低了另一种自动化风险：优化系统为了获得更好的测试评分，悄悄改变功能定义或遗漏困难的边界情形。

## 决定自动设计能否有效的，不是生成速度，而是物理反馈

Frostbite 的快速模拟模型一开始并不可靠。Arcmodel 并不了解所有布局布线约束和物理效应，最差情况下，它对功耗的预测与达到时序要求的 RTL 结果偏差接近 250%。如果 agent 只根据这样的模型调优，反复搜索可能会快速逼近一个虚假的最优架构。设计自动化因此必须先解决一个很现实的问题：用什么反馈信号告诉模型，纸面上的节能真的会变成电路上的节能？

团队建立了自动校准管线。系统先在 RTL 中找到耗能热点，追踪相应的形式化计数器，例如 SRAM 访问、算术操作、片上网络传输、流量控制回复和执行帧未命中。然后它可以构造计数器的标量预测函数，持续比较预测与 RTL 估计，直到误差降至约 5% 以内。不同阶段披露了不同速度数据：ASL 系统模型曾被描述为大约比 RTL 仿真快 200 倍，而校准后用于整芯片探索的 Arcmodel 仿真速度约为 RTL 的 660 倍；这不是两个同一测量条件下可直接互换的结果。

校准后的模型让 agent 能够大量尝试软硬件协同变化。例如，某个 tile 的细粒度时钟门控节省了开关功耗，但也要求软件运行时调整任务安排。若编译器、模型和电路由不同团队按月交接，这种互相制约的改动很难反复试验；在统一的反馈闭环里，它可以成为几小时内的一次候选实验。

此后，原始 Python 模型与那份 141 页方案不再是权威来源。研究团队称，agent 在四轮搜索与最后的消融分析中共测试 58 个候选思路，保留 37 个。候选变化小到某个 tile 的时钟门控、大到 L3 管理表或共享扩展单元的结构。每个思路都要回到契约、Arcmodel、RTL 和功耗评估，经过验证后决定保留或撤销。设计自动化的价值由此从“更快产出代码”，转向“更便宜地探索和否证更多架构假设”。

需要强调，这个物理反馈闭环主要使用的是流片前的综合与布局估计。研究团队也承认，要把功耗预测与真正量产芯片对应起来，还需要未来不同流片批次的校准数据。模型与 RTL 结果在同一套工具内高度吻合，不意味着实际晶圆上的表现已经被验证。

## 4.59 倍究竟比谁快，8.77 倍又衡量什么

Frostbite 已经形成了最终 GDS 物理版图数据，这是制造前的重要交付物，但并不等于已经流片、封装、上电并运行真实程序。团队采用 7 纳米工艺参数进行实现，综合阶段达到 800 MHz 时序，最终版图达到 500 MHz。它的整体布局是一张 4×4 tile 网格；为了近似比较单核规模，性能测试使用其中一个 2×2 tile 的 quad 加四个 L3 节点，对照一个同工艺、面积接近的传统 CPU 核心。

被称为 TCPU 的对照核心面积为 0.895 平方毫米，Frostbite quad 加 L3 为 0.792 平方毫米。TCPU 是一个双发射、顺序执行、研究团队称已由硅芯片验证过的超标量核心；因为法律原因，文章没有披露它的准确型号。这非常关键：4.59 倍不是对所有 Xeon、Zen、Apple Silicon 或现代最高端乱序 CPU 的通用结论。两个参与比较的设计具有特定的面积、实现条件和负载组合，结论只能首先成立在这些边界之内。

在全部 25 项测试上的**每瓦性能比值几何平均数**为 4.59；其中已用于架构搜索的 10 项为 6.02，未参与调优的 15 项为 3.83。把保留测试集单独列出来很重要，它说明性能优势并不完全靠反复迎合调优项目取得。不过这仍不是行业通用工作负载验证，且保留集涵盖的计算类型并不与调优集一模一样，因此两个均值之差本身也不能精确等同于“过拟合程度”。

工作负载之间的差异非常大。按团队公开的图表，保留集里的二维卷积达到约 23.12 倍每瓦性能，而递归 Fibonacci 只有约 1.15 倍。这两个数字清楚说明，这是一种对不同计算形态表现不均衡的架构，而不是所有程序平移过去都能获得近五倍提升。团队另给出全部测试上 **8.77 倍的单位面积性能**指标；这衡量芯片占用面积对应的计算产出，不能与每瓦性能混成一个“八倍更快”的速度承诺。

能耗拆分解释了为什么交互网可能有优势。先剔除时钟分配开销——它在 TCPU 总能量中占 49%，在 Frostbite quad 中占 41%——剩余部分中，TCPU 花约 57% 在存储系统、27% 在取指译码与指令发射；Frostbite 对应比例分别降到 38% 和 6%。相应地，Frostbite 新增了约 26% 的片上网络与调度能耗。计算并没有消灭通信成本，只是把大范围共享状态的管理改造成显式、局部的消息交换。研究团队还展示了扩展到 4×4 tile 时的能量占比变化不大，作为结构能够扩展的早期依据，但尚未给出与大型多核系统的完整生产级对照。

以上结果都是 Architect Labs 自己披露的研发评估。对照处理器不具名、RTL 和完整 ISA 尚未开放，外部研究者目前无法完全复现实验。公司已经把更广泛的 SPEC、PARSEC 负载测试、更大规模网格对照、FPGA 软件演示环境、初步操作系统和 RTL/ISA 开源列为后续工作。这些计划仍然是计划，不应被当成已完成的验证成果。

## 芯片设计的关键变量，从人天变成了可验证的搜索空间

这项研究呈现了一种很不一样的研发成本结构。传统流程里，尝试完全不同的指令集或内存模型，要投入昂贵的架构设计、验证和迁移工作，而且失败之后的大部分工程成果不易复用。Frostbite 通过把编程模型、硬件结构、系统模型和形式化规则绑定为一套共同约束，尝试让更多候选设计在较短时间里得到实际物理估计，再根据反馈被保留或淘汰。

它也重新定义了“AI 自动设计芯片”的能力边界：产出成千上万行硬件代码是一种能力；提出新的局部任务分配规则、将其变成可执行指令、在系统模型中评价、映射成经过检查的 RTL，再把变化反映到物理版图中，是另一种更加系统性的能力。只有后者能支持真正大范围的硬件与软件联合搜索。

同时，Frostbite 并没有证明通用处理器即将整体被替代。新的语言和运行时要面对完整的软件生态、操作系统、虚拟化、I/O、内存容量与大型真实应用；初步测试里的 25 个计算核也无法覆盖这些问题。其最终价值将由可部署的软件栈、可复现的广泛基准与真实硅片决定，而不仅是一次漂亮的模拟结果。

## 延伸判断与启示

Frostbite 最值得延伸的产业判断，是 **AI 对芯片行业的冲击可能先发生在设计方法论，而不一定先发生在某一颗新 CPU 的销量上**。如果自动架构搜索与形式化契约能稳定闭环，芯片设计企业就可以为特定模型、网络协议、工业控制或科学计算负载尝试更多专用的编程模型和硬件组合。由此受益的不只是设计自动化工具本身，还可能包括能提供高质量物理反馈、验证约束、可复用 IP 与软件工具链的企业。与其只看模型生成多少 RTL，更应该追踪每轮可验证探索的成本、可复现性、失败率及最终硅片差距。

但也必须把行业想象与现实可用性分开。Frostbite 的 4.59 倍能效来自不具名对照组和厂商披露的流片前结果；当比较对象换成宽发射乱序 CPU、测试扩展到大型软件系统，或者必须承担完整操作系统与生态迁移成本，优势可能收窄，甚至发生重排。真正决定它能否成为新一类计算平台的，不是“AI 发明了处理器”这句标题，而是独立评测、芯片实测、编译器可用性和客户迁移意愿能否在未来同时成立。
