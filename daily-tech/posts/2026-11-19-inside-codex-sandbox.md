# 不把开发环境关进 Docker：Codex 如何在你的电脑上为 AI 划出真正的安全边界？

2026 年 11 月 18 日，OpenAI 工程师 Michael Bolin 在 OpenAI Engineering 发表[《Inside the Codex sandbox》](https://openai.com/index/inside-the-codex-sandbox/)，全文免费开放。这篇工程深读讨论的并非模型在安全评测中能拿几分，而是一个更接近生产系统的问题：当 AI 编程助手能调用终端、改写本地项目、启动编译器和接触网络，怎样限制这些能力，又不牺牲开发者已有的工作环境？它公开了权限配置、执行框架、网络代理和三种操作系统上的隔离机制。要理解为什么 AI Agent 需要模型之外的安全基础设施，这是一份罕见的具体材料。

## Agent 为什么不能简单搬进一个容器

开发者笔记本往往不只是源代码所在的位置。编译器、SDK、调试器、模拟器、依赖缓存和各类本地服务，可能散落在不同目录。把 Agent 放到一台虚拟机或者 Docker 容器里，确实容易创造隔离边界，却不保证复制原有开发环境。

一个典型场景是 macOS 上的 iOS 应用开发。原生构建链依赖 Mac 可执行程序，开发过程还可能启动 iPhone 模拟器。容器并不能直接取代这些原生能力。即便把构建或模拟器操作转发回宿主机，真正会影响宿主环境的命令还是在容器外执行，因此仍需要一套新的权限控制。

Codex 选择让命令运行在适合任务的原有环境里，借助各平台本身的沙箱能力控制文件和网络，而不是要求每位开发者迁移工作区。这背后是一种产品判断：隔离措施如果破坏真实任务，开发者最终就可能关闭它；能够长期存在的安全机制，必须与日常工作兼容。

沙箱也不是语言模型自己控制的一个提示词选项。模型提出调用工具，负责实际执行的框架 harness 才决定如何创建进程、传入哪些权限、是否接入网络代理。Agent 可以表达想执行什么，操作系统的限制却不由这段表达来解除。

## 默认规则的取舍：读得广，写得窄，网络先关闭

Codex 内置的工作区权限配置叫 :workspace。它允许改写工作区内的业务文件，但把 .git、.codex 等关键目录保持只读，也保护 .agents 和 .aws 等配置目录。这样，正常的代码修改无需每一步都征求用户许可，版本控制元数据、Git hooks 和 Agent 配置却不容易被命令直接篡改。

读取权限比写入宽得多。这不是因为本地所有文件都安全，而是因为构建工具通常需要读取仓库之外的系统 SDK、运行库、工具链和配置。如果只让进程读取项目文件，连普通的编译测试也可能无法工作。允许广泛读取，仍受当前用户账户的系统权限约束，但这意味着本机其他路径中保存的敏感配置和 API 密钥也可能被读到。

为限制这类信息直接流向外部，工作区默认不开放网络。下载依赖和查询在线文档因此也会被阻止，需要按具体需求另行授权。文件读取、文件改写与网络发送被拆成不同的能力，而不是合并成一个粗糙的“可信/不可信”开关。

即便做到这一步，沙箱仍不能保证所有伤害都显现在代码提交记录里。原文展示了本地依赖污染的一条路径：假如 Agent 修改了项目中的格式化程序，改动恰好发生在通常被 Git 忽略的 node_modules 目录，常规 git status 可能看不到任何异常。之后编辑器按用户的正常设置调用该格式化程序，恶意逻辑就可能脱离 Codex 原有的沙箱执行。危险不是沙箱必然被直接突破，而是受信任工具未来执行了被污染的本地内容。

所以权限隔离只能降低一类风险，不能取代模型对用户意图的遵守、供应链保护和下游执行流程的审查。一个操作是否允许、一个文件之后会被什么程序使用，是不同层次的安全问题。

## 真正执行命令的人不是模型

Codex 的核心执行接口接受命令参数、工作目录、环境变量、权限配置以及必要时的网络代理，再返回一个可等待执行完成的子进程对象。对开发者来说，它仍像一次普通命令调用；对执行系统来说，每个命令在被启动前都要经过权限约束。

原本的终端工具可以用普通的子进程启动方法执行 shell，再收集标准输出和退出状态。启用沙箱之后，harness 将启动部分换成受限制的执行接口，其余工具流程保持一致。这让安全控制位于模型提出命令与系统真正执行之间，不必给每一种命令重新发明安全逻辑。

限制需要穿透整个进程树。终端命令经常再启动编译器、脚本解释器或后台子任务。新进程会继承父进程的沙箱约束；即使最初启动它的程序结束，仍然存在的后代也不能因此恢复完整宿主权限。否则，只要让 shell 再启动另一个程序，沙箱便失去意义。

单次命令可以请求更宽的权限。默认情况下继续使用当前会话配置；如果需要访问额外的目录或网络目标，可以提出扩权；完全脱离沙箱的运行则属于更高等级的升级请求。是否批准由执行框架按用户配置决定，可能触发用户确认，也可能走独立的自动审查。模型发出申请，不等于模型拥有审批权。

这套机制也被复用到本地文件的读取和修改等操作，而不限于 shell。它构成了开发工具的共同安全底座：不同工具调用尽可能落在同一套权限语义上。

## 安全配置如何既能本地定制，又不破坏企业底线

权限配置被组织成可命名、可复用的 permission profile，写在 config.toml 的 permissions 部分。开发者可以从 :workspace 派生项目专用配置，在原有规则之上增加需要写入的构建缓存目录，同时把 .vscode、.devcontainer 等路径设为只读，禁止访问环境变量文件和 secrets 文件夹。

规则有读、写、拒绝三种实质差别。工作区内并非只能全盘放开或者全盘封闭，父目录可写并不意味着其中每个敏感子目录都可写。一个更具体的规则能够为包含凭证或工具配置的路径加上额外限制。

工作区根目录的定义也会影响规则覆盖范围。Codex CLI 一般用当前工作目录作为工作区根，ChatGPT 桌面版则根据项目源代码目录确定根。相对路径保护会应用到各个根下面，因此在不同项目布局中，相同的 .vscode 规则可能约束多个目录。

个人项目需要弹性，大型组织还需要统一约束。Codex 的配置可以从多层 config.toml 合并：表结构递归合并，冲突项目由更高优先级来源决定；数组则整体替换。团队可以在基础策略上叠加某个项目的例外，而不必复制全部规则。

管理员还可以通过 requirements.toml 限制最终可供选择的权限配置，例如允许只读模式而禁用完全访问模式。更高优先级的云端托管要求能够覆盖本机设置，用户不能通过修改低优先级配置重新打开被组织明确禁止的能力。权限配置因此既是开发者工具，也可以成为企业执行安全制度的一部分。

## 网络代理真正保护的，是请求发出去之前那一刻

网络模式并不只有允许和禁止。Codex 还支持将所有外部连接限制为经过网络代理，由代理按域名策略决定是否转发。规则可以允许特定域名和子域、明确拒绝其他域名，对没有匹配规则的请求暂停并申请授权。明确拒绝优先于允许，不过广泛通配域名本身也可能产生风险。

代理由 Rust 组件 codex-network-proxy 实现，可以作为框架内的库，也可以构建为独立工具。它默认提供 HTTP 和 SOCKS5 代理，并通过 HTTP_PROXY、HTTPS_PROXY、ALL_PROXY 以及部分应用专用环境变量告知沙箱进程。并不是所有程序都会遵守这些变量，因此操作系统层还要阻止进程直接连接外部主机。仅把环境变量交给程序，是使用约定，不是安全边界。

一个容易忽略的细节是域名解析。即使最终 HTTP 请求没有成功，DNS 查询本身也可能将敏感内容编码到主机名里传出。所以代理必须先检查目的域名是否被允许，再做 DNS 解析，而不是先解析后拦截。若允许任意 DNS 服务或宽泛的通配域名，数据泄露通道仍可能存在。

从这里可以看出，一个受限网络并非“有代理地址”那么简单。它要保证应用程序无法走代理之外的出口，授权在外部解析之前生效，而扩权决策可以交给用户或独立审查。网络控制的安全性取决于整个请求链条，而非其中某一个开关。

## 相同的权限语言，背后是三个完全不同的操作系统

Codex 在 macOS、Linux 和 Windows 上暴露统一的沙箱接口，底层却使用各自的原生机制。它试图让权限配置具有一致的含义，而不是假设不同内核能够执行同一套隔离命令。

macOS 依靠 Seatbelt。这是内核强制执行的沙箱机制，策略使用 Sandbox Profile Language（SBPL）编写，Codex 再用系统的 sandbox-exec 启动命令。基础策略以默认拒绝为起点，对真正需要的文件、设备和指定本地代理端口逐项开放。执行时还可以把工作区路径作为参数注入规则，使同一策略模板适配不同目录。

Seatbelt 的现实处境并不完美。Apple 没有为第三方完整公开 SBPL 的文档，sandbox-exec 的手册甚至标为 deprecated。可系统依然内置相关能力，Chrome 和 Chromium 等软件也仍依赖 Seatbelt。Codex 选择继续使用这一技术，不是因为它毫无长期风险，而是它目前能为原生 Mac 工作流提供可用的内核级约束。

Linux 则组合 bubblewrap 与 seccomp-bpf。bubblewrap 构建隔离文件系统视图和独立的命名空间，seccomp 在系统调用层过滤危险操作。内部的 codex-linux-sandbox 启动器先组织隔离环境，进入环境后再施加系统调用约束，最后执行真正的命令。

在文件层，bubblewrap 可以把某个目录映射为读写、将另一个目录映射为只读，也可以遮蔽完全禁止访问的文件。通配式拒绝规则要先展开成当时存在的具体路径；命令开始运行后才出现的新匹配路径，不会自动加入该次命令已经生成的限制。这个执行时差异意味着，glob 不是一个会持续追踪未来文件的安全观察器。

Linux 的隔离还覆盖进程、IPC 和网络命名空间。网络关闭或者强制代理时，bubblewrap 建立新的网络命名空间；seccomp 再过滤网络相关系统调用或套接字类别。启动器设置 no_new_privs 标志，防止后续执行某些程序时获得额外权限。这样，文件可见性、可调用的内核接口和提权途径都受到限制。

Linux 还面临一个工程难题：沙箱内有独立网络命名空间，如何访问外面的受控代理而不暴露完整的宿主网络？Codex 在沙箱内部建立 loopback TCP listener，用 Unix socket pair 控制通道把监听端口的文件描述符交给沙箱外的桥接进程。外部进程收到沙箱的连接后，再把数据转发给真正的代理。交接完成后，内部启动器关闭不再需要的描述符，施加 seccomp，然后运行用户命令。

这种桥接意味着应用程序只看见自己命名空间中的本地代理端口，不必获得宿主网络可见性。macOS 可以让 Seatbelt 直接放行宿主机特定 loopback 端口，Linux 因为命名空间更加隔离，需要显式地交接监听描述符。相同的产品功能背后，实际上有一套细致的平台适配。

Windows 的故事还在变化。Codex 正逐步从早期依赖宿主访问控制列表与相关设置的方案，转向微软 MXC（Microsoft eXecution Container）提供的原生进程隔离。旧方案可能需要管理员权限、昂贵的 ACL 检查和设置，并在宿主留下一些持久化的权限、网络规则、沙箱用户与控制文件，维护成本并不低。

MXC 通过结构化 JSON 接受命令、工作目录、环境变量与权限策略。Codex 在兼容的 Windows 设备上借助 MXC 限制文件系统、网络和桌面等资源。实现允许必要的注册表读取与 PowerShell 启动所需的 Win32k 能力，却禁止剪贴板访问、输入注入、桌面和系统设置控制，也不允许回退到修改宿主机文件权限的方式来达成隔离。

文件系统默认拒绝访问，但可以对各磁盘根授予只读，让编译器仍可加载系统依赖。工作区可写时，其中 .git 等子路径继续保持只读；不同路径写法或 junction、符号链接指向同一个对象时，优先采用更严格的权限。Windows 的拒绝通配规则同样会在进程启动前展开为具体文件路径，新产生的匹配文件不会自动被追加进已启动命令的列表。

网络仍采用跨平台共享的代理判断逻辑。MXC 阻止直接连接外网，允许通过本机 loopback 抵达代理。但这种设计也意味着某些其他本机服务可能可达，因此网络隔离不能被误读成“沙箱内的进程与宿主上所有服务完全断联”。

## 一个经常被忽略的入口：第三方 MCP 服务器

Codex 把沙箱能力包装成可独立运行的 codex sandbox 命令。开发者不必启动 Agent 会话，也能用某个权限配置执行任意命令，测试哪些文件改写或网络操作会被拒绝。原文给出的实验，就是尝试修改只读的编辑器配置文件，把恶意格式化程序接入自动保存流程；命令被操作系统权限阻止。

更有现实意义的是 MCP（Model Context Protocol，模型上下文协议）服务器。通过标准输入输出启动的 MCP 服务器，不会天然套用 Codex shell 工具的沙箱；执行框架无法仅凭服务器的名字就知道它需要哪些文件和网络权限。如果给所有第三方工具强行套一个狭窄的默认配置，许多本来合法的工具会直接失效。

原文的例子使用一个通过 npx 启动的记忆服务器。默认启动方式下，这个进程可能拥有与当前用户相同的本地文件和网络权限。把它包装进 codex sandbox，并给专门的 memory-mcp 权限配置，就能将写入收缩到 npm 缓存与服务器数据目录，同时禁用外部网络。

这里还有一条部署条件：第一次安装依赖需要网络，禁网环境不能现场下载 npm 包。可在沙箱外预先创建数据目录、预热固定版本的 npm 缓存，随后让 npx 以 offline 模式在受限环境中运行。安全策略要与依赖准备过程一起设计，而非简单地等软件启动失败再给它完全访问权限。

这使沙箱从 Codex 内部的保护手段，变成第三方自动化工具也能复用的本地执行原语。把陌生脚本、工具服务器或项目命令放在明确的文件与网络权限之下，才能在继续扩大 Agent 可用能力的同时，避免每个新工具都继承完整用户权限。

## 延伸判断与启示

这套架构透露出 Agent 产品竞争的一条长期主线：模型会不会写代码只是能力起点，能否持续在真实机器上干活，取决于执行权限、审批机制、进程继承、网络路由、依赖管理与异常恢复能否成为一致而可靠的系统。权限配置越精细，理论上越能减少高风险的永久授权；但如果频繁打断工作或与本机工具不兼容，用户仍然会倾向于绕过它。因此未来可衡量的优势，不只是成功完成多少任务，还包括在受限权限下能完成多少任务、需要多少次人工审批，以及边界失败后能否清晰定位。

另一个启示是，本机执行并不天然比云端虚拟机“安全”或“不安全”，它们解决的问题不同。本机保留开发者环境，系统沙箱限制命令访问，网络代理控制外部发送，组织策略负责不可被个人覆盖的底线。真正的工程协作者需要在这些层次之间保持清晰边界，同时记住原文强调的剩余风险：被污染的依赖仍可能由沙箱外的可信程序在稍后执行。权限隔离必须和供应链检查、敏感数据管理以及关键操作复核一起设计，才能支撑更长时间、更高自主性的 Agent 工作流。
