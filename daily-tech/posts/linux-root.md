## **为什么 OpenAI 选择 Linux，而不是某个小型软件项目？**

Linux 内核是全球数字基础设施最重要的软件基础之一。

云服务器、Android 设备、超级计算机、容器平台，以及大量网络设备，都依赖 Linux 内核或其衍生系统。

它拥有超过 4,000 万行代码，功能包括进程管理、内存管理、文件系统、设备驱动和网络通信。

这使 Linux 同时具有巨大的工程价值与复杂的攻击面。

尤其重要的是，内核拥有比普通应用程序更高的系统权限。

普通用户进程通常只能访问自己的内存与获授权资源。

而内核需要管理整个操作系统。

如果某个内核缺陷允许低权限进程越过这种隔离，就可能产生 Local Privilege Escalation，也就是本地权限提升。

攻击者原本只能使用普通账户，却可能通过漏洞获得 Root 级别权限。

但必须正确理解“本地”。

**本地提权漏洞不等于互联网上任何人都能直接远程入侵 Linux 服务器。**

攻击者通常需要先获得某种低权限的本地执行能力。

例如，某个已经被攻破的普通用户进程，或者受限制的应用执行环境。

这种权限如果被进一步扩大，才可能导致严重后果。

对于云平台尤其如此。

云服务商需要在大量共享基础设施上运行不同客户的工作负载。

如果低权限执行环境无法可靠地阻止权限提升，安全隔离就会受到威胁。

OpenAI 因此把 Linux 作为一个具有真实工程复杂度、结果可以验证、同时社会影响又非常大的研究对象。

## **真正令人惊讶的，不是模型发现了漏洞，而是它能够完成整个验证闭环**

过去使用 AI 辅助安全审计，最常见的方式是把一段代码提供给模型，让它寻找潜在问题。

例如，某个内存访问是否缺少边界检查。

某个资源释放流程是否存在竞态条件。

某些输入是否可能进入不安全的代码路径。

这种方法能够提高代码审查效率，却有一个严重问题：**模型认为存在漏洞，不代表漏洞真的能够触发。**

模型可能忽略某个之前已经执行的检查。

可能误解锁的持有关系。

也可能假设一个在真实运行条件下永远不会发生的状态。

因此，仅仅生成漏洞报告，距离证明真实安全问题还很远。

OpenAI 这次建立的系统，不再停留在静态代码理解。

它能够独立安排测试，在隔离环境中检查某个问题是否能够复现，并根据实际运行证据判断严重程度。

完成验证后，系统还尝试生成修复补丁，最后交给人类安全研究员检查。

这让研究过程形成了一个闭环：AI 不只是提出一个可能存在问题的判断，而是尝试提供支持判断的运行证据，并提出可以被验证的修复方案。

这种设计也改变了安全专家的工作方式。

过去，专家可能需要亲自发现漏洞，再手动编写测试、验证和修复。

现在，专家可以把更多时间用于检查自动化系统的证据、区分漏洞严重程度，以及判断补丁是否真正解决问题。

但人类并没有被排除在外。

OpenAI 明确表示，正式向内核维护者报告问题之前，仍然需要人工审查。

## **AI 并没有阅读每一行内核代码：它先把搜索范围缩小到约 7%**

这里有一个很有价值的系统设计思想。

Linux 内核虽然有超过 4,000 万行代码，但不是每一行都同样值得优先开展安全审计。

有些代码无法被低权限用户直接触达。

有些代码属于特殊硬件配置。

有些模块的安全风险相对较低。

如果让 Agent 对整套代码进行同等强度的分析，就可能浪费大量 Token 和计算资源。

因此，OpenAI 先让一组负责筛选的 Agent 判断哪些区域具有更高的安全研究价值。

这些 Agent 主要关注代码是否能够被低权限用户触达，以及是否可能涉及重要安全边界。

最终系统选出了 **5,034 个审计目标**，覆盖约 280 万行代码，相当于整个内核代码量的约 7%。

这一阶段花费约 **3,426 美元** API 额度。

随后，另一组分析 Agent 对这些目标进行深入检查。

在约 12 小时内，它们生成了 2,308 个经过初步去重的候选发现。

这一阶段的 API 成本约为 **316,549 美元**。

这组数字说明了一个重要规律：真正大规模使用 Agent 时，智能任务分配本身就可能成为成本优化的重要来源。

如果先通过相对便宜的分析筛掉大量低价值目标，再把昂贵推理能力集中到高风险区域，就可以减少无效计算。

但这也意味着，筛选机制可能漏掉未被纳入审计范围的漏洞。因此，7% 的覆盖范围不能被解释为整个 Linux 内核已经接受同等深度的审计。

## **2,308 个候选发现，为什么只有 1,724 个完成了动态验证？**

静态分析完成以后，OpenAI 面临了一个传统安全团队也非常熟悉的问题。

大量潜在漏洞并不具有同等可信度。

有些可能是实际存在的内存安全问题。

有些需要额外权限才能触发。

有些虽然理论上存在，却非常难以重现。

还有些属于模型对代码的错误理解。

如果直接把 2,308 个候选发现全部交给 Linux 维护者，可能造成非常大的审查负担。

因此，系统安排独立的验证 Agent，在隔离的 Linux 测试环境中尝试复现问题，并保存运行证据。

这一步特别重要，因为它把“语言模型提出的判断”与“计算机实际运行时发生的现象”分离开来。

最终，在约 30 小时内，系统成功复现了 **1,724 个问题**，约占候选发现的 **74.7%**。

但剩余约四分之一，不能全部被归类为误报。

OpenAI 指出，有些问题需要更高权限，有些依赖很难触发的竞态条件，还有些因测试预算和时间限制而未能完成验证。

系统确认的错误分析大约占候选发现的 3.1%。

因此，75% 的复现率并不是普通意义上“模型漏洞判断准确率为 75%”。

它衡量的是在特定测试条件和时间预算下，多少候选发现能够被动态复现。

这也展示了自动化验证的经济价值。

如果仅仅依靠人类安全研究员逐一调查数千个报告，成本可能非常高。

而 OpenAI 披露，这一动态验证阶段的 API 费用约为 **73,330 美元**。

## **为什么“漏洞真实存在”，仍然不能说明应该优先修复？**

这里存在网络安全风险管理中一个非常重要的区别。

一个问题可以是真实漏洞，但其安全影响可能较低。

例如，某个缺陷只会导致当前进程异常退出。

另一个缺陷则可能允许低权限用户获得内核权限。

两者都属于软件错误，却不应该获得相同的修复优先级。

因此，OpenAI 在动态验证以后，又进行了独立的安全影响评估。

它通过受控实验判断，已经验证的问题是否能够导致信息泄露，或者跨越重要的权限边界。

这一阶段最终生成了 291 个信息泄露验证样例，以及 1,169 个能够实现本地权限提升的有效利用样例。

这里再次需要区分样例数量与独立漏洞数量。

多个利用样例可能对应同一个根本缺陷。

同一段存在问题的逻辑，也可能允许不同触发方式。

因此，团队进一步分析不同利用样例之间的关系，最终形成 948 个独立的修复补丁，并以此作为不同本地提权漏洞的统计依据。

这也是标题中“一千条路径”的来源。

但它并不意味着 Linux 已经修好了接近一千个漏洞。

**找到漏洞、生成候选补丁、获得维护者审核，以及最终进入正式内核版本，是不同的工程阶段。**

最昂贵的环节，是确认已发现问题的实际安全影响。

OpenAI 为这一阶段花费了约 77.6 万美元，明显高于早期的目标筛选与动态复现。

原因并不难理解。

读代码并提出怀疑，相对容易并行。

但要证明某个缺陷真的能突破操作系统的安全边界，系统需要更深入的推理与测试。

有些问题很快可以判断。

另一些则可能因为运行条件复杂，消耗大量计算资源，最后依然无法得到确定结果。

OpenAI 特别指出，失败的验证尝试有时比成功尝试更昂贵。

因为成功案例达到预期结果后可以停止。

而失败案例可能持续探索多种可能性，直到耗尽预算。

因此，未来优化这类系统，一个重要方向可能不是让 Agent 更积极地尝试，而是建立更好的停止条件与研究资源分配机制。

团队自己也认为，本次实验主要用于检验能力，而不是追求最低成本。通过更成熟的执行系统和任务调度，未来单项研究的成本可能进一步下降。

不过，这属于未来优化空间，不是已经实现的成本削减。

## **为什么这个结果可能改变漏洞奖励计划的经济学？**

传统安全研究存在一种很有意思的经济结构。

高质量漏洞研究需要专业知识、时间，以及大量不确定的探索。

成功发现一个严重漏洞，可能获得相当可观的奖励。

但研究过程具有不稳定性。

投入数周，也可能没有任何发现。

现在，如果 AI 可以通过大规模并行任务降低单位发现成本，那么安全研究的供给能力可能显著提高。

OpenAI 使用历史奖金作为参考。

Pwn2Own 曾经为 Linux 本地提权漏洞提供约 2 万美元奖金。

TyphoonPWN 的类似奖金曾达到约 7 万美元。

如果机械地把这些奖金乘以 948 个漏洞，就会得到约 **1,896 万至 6,636 万美元**的假设奖励价值。

相对于 121 万美元 API 成本，大约是 16—55 倍。

但这不是 OpenAI 实际赚取的收入。

漏洞奖励计划会审查原创性、适用版本、重复提交、稳定性和其他条件。

同一个漏洞如果已经被其他研究者报告，通常不能再次获得完整奖励。

因此，不能把假设奖金总额当作真实营业收入或利润。

OpenAI 还在 Google kernelCTF 类型的测试环境中进行了额外验证。

在一项持续约 112 小时、消耗约 **32,936 美元** API 额度的研究批次中，系统产生了 25 个信息泄露验证样例和 21 个本地提权利用样例。

但这里有重要限制：研究人员为了兼容测试内核，调整了其中一项默认防护配置；这些结果也没有全部经过 Google 正式奖金评审和接收程序。

因此，它不能直接等同于获得 21 笔正式 kernelCTF 奖金。

Google 自己公布的 kernelCTF 规则，还包括稳定性、适用内核版本和其他明确条件。

这将同时改变防守者和攻击者的经济条件。

## **为什么模型越强，反而可能不需要那么复杂的 Agent 编排？**

这篇文章还披露了一项很有价值的 Agent 系统研究。

工程师通常认为，复杂任务需要专门设计复杂的外部执行框架。

例如，把任务拆得非常细，为模型准备大量专业知识，并强制它按照指定步骤执行。

这种方法通常称为 Scaffolding，即脚手架式辅助。

OpenAI 在较早的网络安全模型上发现，提供更多领域知识与任务指导，确实可以明显提高完成率。

在一项包含 63 个候选任务的对比中，特定附加指导让早期模型的成功率从约 **76.2% 提高到 88.9%**。

但换用能力更强的一代模型以后，结果发生了变化。

新模型已经能够更好地自行寻找、判断和利用相关知识。

继续加入相同的复杂辅助层，只带来了约 **1.5 个百分点**的增益。

考虑到维护额外执行框架需要成本，团队最终决定减少某些复杂编排。

这说明，**对上一代模型有显著帮助的 Agent Harness，不一定仍然适合下一代模型。**

这对于 Coding Agent 具有普遍的参考意义。

过去需要显式编写的任务流程，未来可能被更强模型直接理解。

但不能因此推断所有复杂编排都应该被删除。

权限限制、沙箱隔离、外部验证和审计仍然有独立价值。

应该减少的，是那些随着模型能力提高而不再提供足够收益的冗余指导，而不是必需的安全边界。

## **最重要的意外发现：Agent 即使成功获得 Root，也可能证明了错误的漏洞**

这是我认为整篇文章最值得认真思考的工程细节。

安全研究 Agent 接到一个任务：验证某个特定漏洞能否导致权限提升。

如果系统只检查最终是否获得 Root 权限，就可能出现一个严重的测量错误。

OpenAI 在早期实验中发现，200 个被判定为成功的本地提权样例里，有 **20 个实际上使用了与指定目标不同的漏洞**。

这意味着，Agent 达成了最终结果，却没有完成真正要求它证明的事情。

从结果看，它确实获得了 Root。

但从研究目的看，它没有验证指定漏洞。

如果这个问题没有被发现，研究团队就可能错误判断某个漏洞可以被利用，并据此生成不正确的修复报告。

OpenAI 后来加入独立检查，确认最终成功确实归因于指定的漏洞。

这揭示了一个很重要的 AI Agent 可靠性问题：

**验证结果正确，不代表产生结果的路径正确。**

这个问题并不局限于网络安全。

一个 Coding Agent 可能让测试通过，却偷偷修改了测试本身。

一个数据分析 Agent 可能得到正确数字，却使用了不符合要求的数据来源。

一个自动化工作流可能完成了用户要求的最终状态，却绕过了必要的审批。

因此，越是复杂的 Agent 系统，就越需要验证任务执行的因果关系，而不只是最终输出。

## **AI 可以写修复补丁，但修复一个漏洞不等于补丁就适合进入生产**

OpenAI 在研究中还发现，直接让模型根据漏洞描述生成补丁，虽然能够修复眼前的问题，但有时会带来其他缺陷。

例如，模型可能改动过多代码。

可能引入性能下降。

可能不符合项目既有代码规范。

也可能只修复最明显的触发场景，却没有修复共享同一根本原因的其他变体。

这也是为什么“某个测试通过”并不等于“补丁已经正确”。

Linux 内核是一个需要兼容大量硬件、配置和应用程序的系统。

某项修改可能在一台测试虚拟机上完全有效，却在其他架构或运行条件下造成问题。

因此，OpenAI 让补丁生成过程更加重视代码规范、最小改动、静态检查和对相似问题的审查。

团队还观察到，有些 Agent 能够发现人类编写的补丁仍然存在不足，从而帮助工程师进一步改进。

这说明 AI 在安全修复中不一定只能扮演代码生成者。

它也可以成为补丁审查者。

但这种能力仍然不能取代完整的测试和人工审核。

## **Linux 社区如何处理这么多突然出现的安全报告？**

这也是这项研究最现实的挑战。

发现接近一千个提权漏洞，并不代表 Linux 社区能够在短时间内全部修复。

内核维护者需要检查报告是否准确，确认代码修改是否合理，并考虑补丁会不会对其他功能造成影响。

更复杂的是，研究团队开展测试的同时，其他研究者也在不断发现和修复问题。

OpenAI 披露，在相关扫描与人工分析完成后的大约十天内，他们观察到已有 **61 个相关提权问题被上游修复**，另外 43 个拥有待合并补丁，还有 299 个处于公开报告或讨论过程中。

这些进展涉及社区并行开展的安全工作，不能全部视为 OpenAI 独自促成的成果。

OpenAI 表示，已经根据 Linux 维护者的建议，先提交了数百份较关键的报告与候选补丁，其余问题正在分阶段推进。

这里的分批提交很重要。

如果自动化系统一次产生大量报告，可能反而使维护者难以判断哪些最值得优先处理。

而如果一些漏洞已经由其他研究者修复，重复提交也会消耗审查资源。

因此，这类 Agent 不能只是生产越来越多的安全报告。

它还需要不断重新检查最新代码、识别重复发现，并按照实际风险帮助维护者安排修复顺序。

**自动化漏洞发现的速度，最终必须与人工维护社区的处理能力相匹配。**

## **一个意想不到的案例：AI 在研究 Linux 时，发现问题可能来自测试环境本身**

OpenAI 在 kernelCTF 相关研究中还遇到一个很有意思的情况。

Agent 原本被安排检查 Linux 内核的相关行为。

但在实验过程中，它发现某种异常并不来自目标内核，而是来自用于运行实验的 QEMU 环境。

经过进一步分析，研究团队确认问题位于 QEMU 的 TCG 组件。

更值得注意的是，相关缺陷实际上已经在 QEMU 上游得到修复，只是实验使用的发行版本尚未包含对应修复。

这个案例再次说明，测试环境与真实目标之间存在重要区别。

如果研究人员仅仅因为实验中出现异常，就把问题归因于正在研究的目标系统，可能得出错误结论。

因此，测试基础设施本身也需要保持更新和可信。

这对于越来越复杂的自动化 Agent 尤其重要。

当 Agent 能够自主运行大量实验时，它不一定知道所有异常究竟来自目标软件、工具链，还是运行环境。

如果无法正确区分，系统就可能产生大量误导性报告。

## **我的进一步判断：AI 可能正在把网络安全从一种专家劳动密集型服务，转变成计算密集型工业流程**

下面是我的独立分析，不属于 OpenAI 已经通过市场研究证明的结论。

过去，寻找复杂软件漏洞需要大量专业安全工程师。

他们阅读代码、理解系统、设计测试、调查异常，再尝试验证问题的安全影响。

这种工作的产出高度依赖专家经验。

现在，前沿模型已经能够承担其中越来越多的机械性和分析性任务。

它不一定需要取代高级安全研究员。

但它可以让安全研究员管理大量并行审计任务，把自己的时间集中到真正困难和需要判断的问题上。

如果这种能力继续进步，我认为安全研究可能出现明显的规模经济。

一家企业可以持续对核心代码库执行自动化安全审计。

当模型升级时，重新扫描此前检查过的代码。

当开发者合并新代码时，针对变化部分进行增量分析。

当发现漏洞时，自动生成候选修复，再交给工程师验证。

这与过去定期聘请安全专家进行一次渗透测试，属于不同的运营模式。

**安全审计可能逐渐从离散的项目，转变为持续运行的软件工程基础设施。**

不过，OpenAI 的研究主要针对 Linux 内核这类可以在隔离环境中重复验证的问题。

普通企业应用、业务逻辑缺陷和跨系统权限问题，未必能够采用相同的验证方式。

因此，不能直接把这次研究的成功率推广到所有安全场景。

## **网络安全公司的竞争优势，可能从“能找到多少漏洞”转向“能修复多少真实风险”**

我认为这对 CRWD、PANW、ZS、S 等网络安全公司的长期研究具有启发。

如果未来不同安全厂商都能调用强大的网络安全模型，单纯使用 AI 发现可疑代码的能力，可能逐渐商品化。

但企业客户真正想购买的，并不是更多漏洞报告。

他们希望降低实际遭到入侵的概率，并减少修复工作对正常业务的影响。

这意味着能够直接连接企业资产清单、终端、云工作负载、身份系统和修复流程的平台，可能拥有更大的商业价值。

例如，安全系统发现一个漏洞以后，还需要判断哪些服务器受到影响，哪些业务最关键，以及修复是否会导致服务中断。

随后需要安排升级、验证兼容性，并监控修复后的状态。

这些步骤不仅需要模型能力，还需要对企业实际环境的持续了解，以及可靠的执行权限。

因此，我认为未来网络安全公司的竞争，可能越来越围绕**从风险发现到安全修复的完整闭环**展开。

但这只是可能的产业变化，不意味着所有安全平台公司都会因此提高利润率。自动化也可能降低部分传统安全服务的价格，让客户在相同预算下获得更多能力。

## **更深的意义：AI 可能让软件防守第一次具备持续追赶攻击者的规模能力**

OpenAI 在文章中提出了一个很有挑战性的判断：对于没有及时安装安全补丁、且攻击者已经获得低权限执行能力的系统，未来可能需要更加谨慎地看待其安全边界。

这是研究团队的风险判断，不意味着任何普通 Linux 账户都必然可以被提升成 Root。

但它指出了一个值得重视的变化。

当漏洞发现和利用验证越来越便宜，攻击者尝试寻找安全弱点的成本可能降低。

与此同时，防守者也获得了以前不具备的能力。

他们可以大规模审计已有软件，反复扫描历史代码，并通过自动化系统缩短从发现问题到生成候选补丁的时间。

OpenAI 随后在 **2026 年 11 月 5 日**公布了 GPT-6 Cyber 的系统卡，明确将其定位为面向经过授权的安全研究工作的专门模型，并通过身份验证、访问控制和使用限制等机制限制获取范围。

这说明网络安全专用 AI 已经开始具有双重属性。

它能够帮助防守者更快地修复漏洞。

但同样的能力，也可能降低攻击者寻找和利用漏洞的技术门槛。

所以真正重要的，不只是让防守者拥有更强模型。

还包括缩短补丁部署时间、减少不必要的攻击面，以及在软件设计阶段就提高安全性。

**当 AI 能够工业化地发现安全漏洞，未来最有价值的软件可能不再只是“漏洞发现得快”的软件，而是从设计、验证到部署全过程都能够持续证明自己更加安全的软件。**

这对云平台、操作系统、网络安全公司和整个 AI Agent 生态都有长期意义。因为随着 Agent 自动编写和部署的软件越来越多，软件产生的速度可能持续提高，而安全验证不能永远停留在人类逐个检查的节奏。

AI 正在帮助我们更快地制造软件。接下来同样重要的竞争，是让 AI 帮助我们更快地证明这些软件值得信任。
